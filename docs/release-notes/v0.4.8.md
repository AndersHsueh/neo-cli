# v0.4.8 —— 恢复会话时图片丢失占位编号对齐 chip

> 证据：`docs/evidence/v0.4.8-{tsc,tests}.txt`（tsc exit 0 · 1073 pass / 0 fail / 69 文件）

## 为什么

粘贴图片进会话时，用户看到的是 chip `[Image #1]`、`[Image #2]`……
落盘时按 part 下标命名 `attachments/<id>/img-<i>.png`，恢复时按 `$ref` 重组回 data URL。

附件文件丢失（清理过 `.neo/sessions/attachments`、换机器拷贝会话、手工删文件）时，
`hydrateMessages` 会降级成文本占位 `[Image #N 已丢失]`。原来的 N 用的是**「第几个丢失」**计数器：

```
用户原始输入：[Image #1]（img-0，还在）[Image #2]（img-1，丢）[Image #3]（img-2，丢）
旧行为占位：  [Image #1 已丢失]  [Image #2 已丢失]   ← 全部前移一位
新行为占位：  [Image #2 已丢失]  [Image #3 已丢失]   ← 与 chip 一致
```

前面只要有一张图还在，后面所有占位编号就整体前移。模型看到的是「#1 丢了」，
而用户明明发过 #1、丢的是 #2 —— 追问「第一张图里那个字段」时对不上号。

## 改了什么

`src/session.ts` `hydrateMessages`：序号在每个 `image_ref` 上递增，**无论文件在不在**；
只有「文件缺失」这一个分支消费该序号。跨消息连续（同一会话内 chip 计数不重置）。

## 测试

新增 `tests/session-hydrate.test.ts`（4 条）：

| 用例 | 断言 |
|---|---|
| 前面有图还在时，丢失占位仍按原 chip 编号 | 第 1 张还在 → 占位是 `#2` `#3` |
| 全部丢失时编号从 1 起 | 与 chip 一致 |
| 编号跨消息连续 | 第二条消息的占位接续计数 |
| 非图片消息原样返回 | 不产生占位、不改 content |

红阶段证据：改实现前 3 条失败（`[Image #1 已丢失]` vs 期望 `#2`），改后 4 条全绿。

## 没改的

- 占位文案、`$ref` 命名规则、`saveSession` 落盘格式均不变，旧会话文件直接兼容。
- 不处理「非 PNG 的 data URL」与「同一 part 下标重名」等既有边界（未在本版范围内）。
