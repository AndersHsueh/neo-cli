# v0.4.45 — formatTokens P 档末档补整数档

## 问题

v0.4.44 给 `formatTokens` 补 P 档时，末档只写了 `fixed1(v / 1e15)`，漏了「整数档」那一半。`fixed1` 只负责把 `10.0` 降级成 `10`，不负责把 `1000.0` 收成整数，于是：

| 输入 | 旧输出 |
| --- | --- |
| `1e18` | `1000P` |
| `1e19` | `10000P` |
| `1e21` | `1000000P` |

宽度随数量级无限增长，且与 k/M/G/T 档的「<10 一位小数 / ≥10 整数」两档结构不一致。这与 v0.4.31 修 M 档、v0.4.44 修 T 档是同一类缺陷：**末档也必须有两档结构**。

## 改动

- `src/tui/status.ts`：P 档拆成 `<10P` 一位小数 / `≥10P` 整数两支
- `tests/tui-status.test.ts`：P 档末档边界 7 条（9.95P / 9.96P / 10P / 100P / 150P / 1000P / 1000000P）

## 已知未修（留作候选，不在本轮范围）

1. **P 档以上没有封顶**：`1e300` 仍输出 `1.0000000000000001e+285P`（301 字符）。末档整数档在 1e21 以上依赖 `Math.round` + `String()`，会退化成科学计数法；`toFixed(0)` 同样在 1e21 以上退化（JS 规范）。要彻底解决需要末档封顶或十进制展开，属于改口径，需先定策略。
2. **`formatBytes` 末档 P 同样只有一位小数档**：`1024P → "1024P"`、`1024**7 → "1048576P"`。代码注释写着「末档 P 无处可升，保留 1024P」，是有意为之的口径，动它需先确认。
