# v0.4.17 —— `@path` 引用按字节截断时不再产出乱码

> 证据：`docs/evidence/v0.4.17-{tests,tsc}.txt`

## 为什么

`@path` 引用有 60KB 总字节预算（`DEFAULT_MAX_BYTES_TOTAL`）。超预算的文件按剩余预算
**截断**而不是整份丢弃（PRD C3），截断走 `defaultReadSlice`：读前 N 个**字节**，再
`new TextDecoder().decode(...)`。

问题在最后一步：默认 `TextDecoder` 遇到残缺的多字节序列会替换成 `U+FFFD`（替换字符）。
中文 3 字节、emoji 4 字节，截断点很容易落在字符中间。

实测（`maxBytesTotal: 100`，文件是 90000 字节的全中文）：

| | 修复前 | 修复后 |
|---|---|---|
| 正文尾部 | `…中中中�`（乱码） | `…中中中` |
| 引用块字节数 | **102**（超预算 2 字节） | 99（在预算内） |

两个后果：

1. **乱码进了模型上下文**——`U+FFFD` 看起来像文件真实内容的一部分，模型可能据此
   误判文件里有什么；
2. **字节预算被突破**——`Buffer.byteLength("�")` 是 3 字节，比请求的 1 字节多 2，
   调用方刚算好的 `remaining` 被悄悄撑破。

## 改了什么

`src/input/references.ts` 的 `defaultReadSlice`：

```ts
return new TextDecoder("utf-8", { fatal: false })
  .decode(buf.subarray(0, n), { stream: true });
```

`stream: true` 表示「这是流的一段，末尾不完整就留着别解码」——残缺尾部直接丢弃，
只交出已完整的前缀。`fatal: false` 保留：文件本身若含非法字节，仍按替换字符处理
（那是文件的问题，不是截断的问题）。

语义上这比修复前更准确：截断后的正文是「原文的完整前缀」，而不是「原文前缀 + 一个
凭空造出来的字符」。

## 为什么之前没测到

`tests/references.test.ts` 原有的两条超预算用例都**注入**了 mock：

```ts
readSlice: (p, n) => files[p]!.slice(0, n),   // 按字符切，不是按字节
```

mock 按字符切，永远切不到多字节字符中间，`defaultReadSlice` 的真实实现从未被覆盖。

## 测试

新增 `C3d` 两条用例，**不注入** `readSlice`，走真实实现 + 真实临时文件：

- 全中文文件、预算 100 字节 → 断言正文无 `U+FFFD`、正文字节数 ≤ 预算；
- `abcde😀😀`、预算 7 字节（正好切在 emoji 第 2 字节）→ 断言正文恰为 `abcde`。

红相已验证：撤掉修复后两条均失败（`abcde�`、102 > 100），恢复后通过。

全量 **1095 pass / 0 fail**（较 v0.4.16 的 1093 增加 2），`tsc --noEmit` 干净。
