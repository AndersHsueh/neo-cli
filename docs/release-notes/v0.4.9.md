# v0.4.9 —— 证据前缀取自 package.json，不再手写

> 证据：`docs/evidence/v0.4.9-{tsc,tests,pty}.txt`（tsc exit 0 · 1074 pass / 0 fail / 69 文件 · PTY 21/21）

## 为什么

`scripts/verify.sh` 的 `EVIDENCE_PREFIX` 是手写常量，注释写着「每版更新」。
从 v0.4.5 到 v0.4.8 连续四版都没更新，一直停在 `v0.4.4`：

- 这四版跑闸门，证据全写进 `docs/evidence/v0.4.4-{tsc,tests,pty}.txt`，**互相覆盖**；
- 同时 `docs/evidence/v0.4.8-*` 是手工落的，与闸门产物不同源；
- 发布说明里引用的证据文件名，和跑一次闸门实际产出的文件名对不上。

版本号本来只有一个真源（`package.json`，`src/cli/version.ts` 也是读它），
证据前缀没理由再维护第二份。

## 改了什么

`scripts/verify.sh` 第 20–28 行：

```bash
EVIDENCE_PREFIX="v$(sed -n 's/^[[:space:]]*"version"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p' "$ROOT/package.json" | head -n 1)"
if [ "$EVIDENCE_PREFIX" = "v" ]; then
  echo "FAILED: 无法从 package.json 解析 version（证据前缀）" >&2
  exit 1
fi
```

- 用 `sed` 取第一处 `"version": "..."`，不引入 `jq`/`node` 依赖（脚本只要求 bash + bun）；
- 解析失败**直接失败退出**，不退化成空前缀——否则会写出 `-tsc.txt` 这种文件，比写错前缀更难排查；
- 其余逻辑（`run_stage`、三阶段顺序、失败即停、`ALL GREEN`）一字未动。

## 验证

- `bash -n scripts/verify.sh` 语法通过；
- 前缀解析实测：`package.json` → `v0.4.9`；构造无 `version` 的 JSON → 得到 `v`，走失败分支；
- `bash scripts/verify.sh` 全量闸门 **ALL GREEN**，产出 `v0.4.9-{tsc,tests,pty}.txt` 三份（此前会写进 `v0.4.4-*`）。

## 没改的

- `package.json` 版本号未动（仍 0.4.9），本次不 commit、不 tag；
- `tests/README.md` 的基线数字未动（本轮 1074 pass 与记录一致，无新增用例）；
- 未加「证据前缀与版本一致」的单测：`docs/evidence/` 在 `.gitignore` 里，测试去断言闸门产物属于跨层耦合，收益低于成本。前缀解析本身已在上面用反例验证过。
