# v0.4.79 — max_tokens 安全防护：启动告警 + 不透明 400 安全降级（issue #21）

## 背景

issue #21：settings.json 里某 provider 把 `max_tokens` 配成与 `context_window` 相同的值（512000），网关对每个请求都返回 400 `"request was rejected by an internal MaaS component"`，`neo -p` 全部失败。

v0.4.75 的 `parseMaxTokensLimit` 只修好了「网关明说上限」的一类（文案同时含 max tokens 语义与可解析数字）；对这种**完全不透明**的 400 文案返回 null，而 400 又不在重试列表里 → 整个会话发不出请求。issue 的另外两项期望（启动告警、文案提示）也未落地。

## 改动

- **A 启动期告警**（`src/config.ts` 新增 `auditMaxTokens`，`src/index.ts` 启动块打印）：加载配置时逐 provider 体检——`max_tokens ≥ context_window` 或 `max_tokens > max_output_tokens`（比较双方非 null 才判，瘦网关没声明就不猜）→ 给出指明 provider/字段的告警。只告警不改配置；模板默认 8192/200000 不误报。结果存 `cfg.maxTokensWarnings`。
- **B 不透明 400 安全降级**（`src/llm.ts` 新增 `shouldDowngradeForOpaque400` + `OPAQUE_400_DOWNGRADE_FLOOR=8192`）：400 且文案解析不出上限、非上下文超长/鉴权/parallel_tool_calls 拒绝时，把 max_tokens 夹到 8192 **重发一次**（chat 与 chatStream 同口径）。硬约束：一次上限不循环；只降不升（当前值 ≤8192 原样透传）；降级值**仅本次请求生效，不写 learnedMaxTokens**——网关明说的上限是稳定陈述可以记忆，单次观察固化会永久污染该 provider+model；降级后仍失败则原始 400 文案如实透传。
- **C 文案与模板**（`src/llm.ts` `appendMaxTokensHint` + `settings.example.json`）：400/422 报错在不改写原始文案的前提下追加一行「部分网关对过大的 max_tokens 会回不透明的 400…」提示（鉴权/parallel 拒绝不加）；模板新增 `max_tokens_note`（输出预算 ≠ 上下文窗口），`capability_note` 补写「max_output_tokens 也不是上下文窗口」。

## 取值口径

降级地板 8192 = settings.example.json 的默认 max_tokens：项目对「保守但可用输出预算」的既有默认，不引入第三个魔数；issue 实测网关对 16384 都返回 200。刻意不用 contextWindow 比例——探测兜底的 200,000 不是事实，拿猜测当基数只会放大猜测。
