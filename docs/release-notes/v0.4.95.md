## 为什么发这一版

v0.4.94 之后 main 上有三组已合入、尚未发版的提交：#71 实验性 Code Mode（`run_js`）、#71 P2 随访，以及 #81 K45b 把纯叶适配委托给已 pin 的 `@neo/core-compat` 扩展归档。功能提交与发版提交分开：**本提交仅改版本元数据及文档，无新增运行时行为**，不改源码、测试、ACP 或 settings。不宣称与 Claude Code 兼容。

## 变更

1. `38819cfa5ce48143d1a97f5eeb90b152f5ac07f9`（feat: 实验性 Code Mode（run_js）批量调用工具，#71）：
   - 默认关闭的实验开关 + 第一方工具 `run_js`：模型可以写一段 JavaScript，在一次调用里批量调用现有工具，而不必逐个 tool call。与普通工具调用共存。
   - 开关：默认关；`NEO_EXPERIMENTAL_CODE_MODE=1` 开启，`=0` 一律获胜（含覆盖用户 settings）。仅当实际载入路径是 `~/.neo/settings.json` 且 `experimental.code_mode === true` 时，settings 才能开启。工作区 `./settings.json`、启动目录、包内 `pkgRoot/settings.json` 都不能开。不改分层合并。
   - 只开交互 TUI。开启后 `/tools` 与提示词「可用工具」行列出 `run_js`。`-p`（即使带 `-y`）、ACP、规划态、子代理、wiki worker 都不暴露。本单不改 `src/acp/*`。
   - 只支持 JavaScript。脚本 API 为 `await tools.read_file({ path })`，名字与注册表一致（含 `mcp__*`）。不兼容 Claude Code 的 `$` / `edit()`，不翻译 TypeScript；非法语法明确失败。
   - 运行器是本进程 `AsyncFunction`，只注入 `tools` 与 `console`，不把 `ctx` / Agent / 内部对象交给脚本。不做假隔离（不使用 ShadowRealm，也不删除/冻结 `process` / `Bun` / `globalThis`）。
   - **残余风险（接受并写进 README）**：脚本跑在本进程，可能读到 `process.env`（含密钥），并直接使用宿主 API 绕过工具闸门。产品不做沙箱，不把沙箱列为待办。
   - 脚本可见工具 = 本轮 `toolSpecsFor()` + 已注册但尚未装入的 `mcp__*`，去掉 `run_js` 自身，也不暴露 `task` / `compact_ctx` / `ask_user` / `submit_plan` / `exit_plan_mode`。内部调用走既有 `dispatch` → `gateTool`，并补打 `tool_start` / `tool_end`。
   - 权限上 `run_js` 与 `shell` 同桶：`ask` / `auto-edit` 要先审整段代码，`auto-all` 放行，`plan` 拒绝。`sensitive` 单独不够。不做整段脚本分类器。内部调用次数上限对齐 `max_tool_iterations`；墙钟 10 分钟（含审批等待）；只有 `isParallelizable` 的工具才真正并行。
   - 返回值 + 捕获的 console，再走 `limitOutput`。P1 不做后台长脚本。不宣称与 Claude Code 兼容。

2. `3d009fba09ed5373bbc165f5bc5e7a8c6d707ba2`（fix: Code Mode P2，#71）：
   - PromptManager 省略 `nonInteractive` 时改为 fail-closed（视为非交互，提示词与 request specs 都不列 `run_js`），避免 ACP 提示词列出无法调用的 `run_js`。交互 TUI 必须显式传入 `false`。仍不改 `src/acp/*`。
   - 规划态 `/tools` 按 `codeModeExposed` 过滤：为 false 时从名单去掉 `run_js`，并继续传入真实的 `agent.planning`，因此规划态不再列出 `run_js`。
   - 生产 `ui.confirm` 与 `approve` 透传可选 `AbortSignal`。已中止则不调 asker；等待中 abort 以 `AbortError` 结束（不是「用户说 No」），并关掉 `[y/N]` 模态。TUI 走 `finishAsk()`；readline 路径使用 `rl.question` 的 AbortSignal option。

3. `9675035b0eb9f3db4ae1b7588b47f9599f489719`（#81 K45b: pin expanded compat/v1 and delegate pure leaves）：
   - 把 K45b 的 `@neo/core-compat` 归档纳入 vendor，并对纯叶做薄适配：`maxTokens` 的 classify/clamp、prompt 的 select/tokens/tiers、Anthropic wire 转换、fallback 归因。Agent 循环与带状态的运行时仍留在 legacy 侧。不是面向用户的新能力，也不改 ACP 协议。

## 验证

本地 Linux release worktree、清空残留 NEO_* 环境后运行 verify.sh。全新 worktree 按流程先执行 `bun install --frozen-lockfile`。安装后、改版本前的官方闸门见 `verify-after-install.txt`（当时 package.json 仍为 0.4.94）：tsc exit 0，2479 pass / 3 skip / 0 fail（147 文件），PTY 36/0，ALL GREEN；D1 通过（72.10ms）。改完版本后的官方闸门见 `verify.sh.log`，版本证据前缀为 v0.4.95：tsc exit 0，2479 pass / 3 skip / 0 fail（147 文件），PTY 36/0，ALL GREEN；D1 通过（70.29ms）。三条 skip 均为 worktree 下 prompt-tiers 找不到 bot-comments 源文件的既有豁免。

**D1 直述（必须保留）**：`oneshot-drive` 测试 D1（缺 `-y` 时预期零模型请求）存在**间歇性、根因未定**的失败。v0.4.94 发版说明已记录更早轮次的观察。本版相关官方闸门补充如下：#71 功能提交在合入前的第一轮官方 verify 为 2460 pass / 3 skip / 3 fail，失败项为 D1 以及确定性的 H1（`src/config.ts` 导出守卫）与 S1（源文件行数上限）；H1/S1 已在第二轮前修好，第二轮为 2463 pass / 3 skip / 0 fail（145 文件）、PTY 36/0、ALL GREEN，其中 D1 通过（71.57ms）。#71 P2 变基前第一轮官方 verify（38819cf + 未提交 P2）为 2471 pass / 3 skip / 1 fail，唯一失败是 D1（`hits` 期望 0、实际 1）；同树第二轮跑到一半被变基指令打断；接到 `9675035` 之后为 2479 pass / 3 skip / 0 fail（147 文件）、PTY 36/0、ALL GREEN，D1 通过（67.12ms）。本发版 worktree 的官方闸门（安装后基线与改版本后）D1 结果见上，即使本轮通过，也**不能宣称已修好**。**官方绿不等于 D1 已解决**，根因仍未定位。D3 与 D1 不混同。
