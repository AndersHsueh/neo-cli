# v0.4.46 — sanitizeOutput 补 OSC/DCS 剥离

## 问题

`sanitizeOutput`（`src/ui/toolLog.ts`）负责把工具输出里的控制序列剥掉再回显。旧实现只有一条通用转义 `\x1b[@-_]`，它只吃掉「ESC + 一个字符」。

而 OSC（`\x1b]0;title\x07`）与 DCS/SOS/PM/APC（`\x1bP...\x1b\\`）都是「ESC + 引导符 + 正文 + 终止符」的**多字符**序列。于是引导符被吃掉、**正文残留**：

| 输入 | 旧输出 | 应输出 |
| --- | --- | --- |
| `a\x1b]0;窗口标题\x07b` | `a0;窗口标题b` | `ab` |
| `a\x1b]8;;http://x\x1b\\link\x1b]8;;\x1b\\b` | `a8;;http://xlink8;;b` | `alinkb` |
| `a\x1bP1;2\|data\x1b\\b` | `a1;2\|datab` | `ab` |

这不是理论问题：带颜色的工具会发 OSC 8 超链接，终端标题同理，`/last` 回看时就会看到 `0;title`、`8;;http://x` 这类垃圾串，既污染可读性，也把宽度算错。

## 根因

**同一条纪律在项目里已经写对过两遍**，`sanitizeOutput` 漏了：

- `src/tui/ansi.ts:225`（`stripAnsi`）：`/\x1b\][^\x07\x1b]*(?:\x07|\x1b\\)/g`
- `src/ui/theme.ts:194`：同一模式

这与 v0.4.16 抽出 `ui/format.ts` 的动机一致 —— 纪律只写在注释里、各处各写一遍，就必然有地方漏。本轮只补 `sanitizeOutput`，**没有**顺手把三处合并成共享实现（那属于重构，且 `stripAnsi` 与 `sanitizeOutput` 的职责不同：前者不保留换行、不展开 tab、不剥 C0）。

## 改动

- `src/ui/toolLog.ts`：`sanitizeOutput` 增加两条剥离规则，顺序在 CSI 之前
  - OSC：`/\x1b\][^\x07\x1b]*(?:\x07|\x1b\\|$)/g` —— 比 `stripAnsi` 多一个 `|$` 分支，**未终止的 OSC（输出被截断）吃到结尾**，不残留正文
  - DCS/SOS/PM/APC：`/\x1b[P^_X][^\x1b]*(?:\x1b\\|$)/g`
  - 末尾补 `/\x1b/g` 剥裸 ESC（与 `stripAnsi` 同口径：不构成合法转义时同样不可见、且会污染终端状态）
- `tests/toollog.test.ts`：新增 3 条（OSC 标题/超链接/未终止、DCS/SOS/PM/APC、裸 ESC）

## 已知未修（留作候选，不在本轮范围）

1. **C1 控制字符未处理**：`\x9b`（C1 CSI）、`\x9d`（C1 OSC）不经 ESC 引导，直接出现在输出里时正文残留（`a\x9b31mb` → `a31mb`）。C0 剥除范围 `[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]` 不含 C1（0x80–0x9f）。实际影响低：UTF-8 终端几乎不发裸 C1。修它需要改剥除范围，可能误伤合法多字节文本，需先确认口径。
2. **`formatBytes` 末档 P 无整数档**：`1024**6 → "1024P"`、`1e21 → "888178P"`、`1e300 → "8.881784197001253e+284P"`（300+ 字符）。代码注释写明「末档 P 无处可升，保留 1024P」是有意口径；但科学计数法漏出是真问题。与 `formatTokens` 的 P 档封顶是同一个口径决策，需一起定。
3. **`clock` 极端值宽度失控**：`clock(1e300) → "2.777777777777778e+296:36:00"`。同上，属末档封顶口径。
