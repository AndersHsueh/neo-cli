# neo 记忆系统设计（提案 v0.1）

> 状态：提案，未实施。等社长拍板后再动手。
> 日期：2026-10-15
> 依据：已读全部源码（6866 行）+ 实测 32 份真实会话 + 外部方案核实（Claude Code 记忆机制 / Mem0 / Graphiti）

---

## 1. 现状盘点（已验证）

代码里与「记忆」沾边的东西共三处，彼此独立，没有统一抽象：

| 位置 | 机制 | 实际行为 | 缺口 |
|---|---|---|---|
| `src/session.ts` | 会话 JSON 落盘 `~/.neo/sessions/` | 完整消息数组，32 份实测存在 | **只用于 `--resume`，从不参与记忆提取**。信息量最大的一处完全闲置 |
| `src/index.ts:326-334` | `AGENTS.md` 注入 | 在 cwd 找第一个命中的文件，**全文无截断**拼到system prompt 尾部 | 无检索、无容量上限、无冲突处理。且只认 cwd 根目录，子目录不生效 |
| `src/agent.ts:126-172` | `compact()` | 超阈值把历史压成一条 user 消息 | 会话内摘要，进程退出即丢。压缩内容也不回写磁盘 |

三个具体的结构性问题：

1. **`noteModelChange()` 与记忆注入会互相干扰**。`agent.ts:113` 用正则 `/- 模型：[^\n]*/` 改system prompt。记忆若也做尾部拼接，两处都在动同一段字符串，顺序错了会把记忆内容吃掉或截断。
2. **会话恢复时记忆会重复叠加**。`index.ts:317-321` 恢复历史后，`326` 行再注入一次记忆文件 —— 若记忆内容曾以 user 消息形式进过历史，会出现两份。
3. **`/init` 生成的记忆文件无人维护**。`buildMemoryFile()` 输出「（待填写：…）」占位符，纯人工。实测 `~/.neo/` 下**不存在任何 AGENTS.md**，即当前环境这条路径完全空转。

## 2. 要回答的三个问题

设计之前先确认问题边界。这三个问题的答案决定了架构，不是反过来。

**Q1：记忆是给谁看的？**
- 给模型：它需要在开工前知道「这个项目怎么跑测试」「这个人不要什么收尾语」。
- 给人：需要能读、能改、能删。

这两个诉求冲突。给人看的东西要可编辑散文，给模型看的东西要结构化可检索。**结论：双层。**

**Q2：什么时候写？**
- 手动写（用户主动 `/remember`）：可靠，但没人愿意反复写。
- 自动抽（每轮让LLM 自己判断）：覆盖全，但会产生垃圾条目，且每次都要额外 LLM 调用（有成本 + 延迟）。

**Q3：什么时候读？**
- 全量注入：简单可靠，代价随记忆量线性增长。
- 检索注入：省token，但需要判断「相关」——而判断相关本身又要花一次调用，或者用不可靠的关键词匹配。

Q3 是关键。**Q3 答错，整个系统就是负资产**：记忆越存越多，每轮都往上下文里塞，挤掉真正的对话内容，最后既费钱又降低效果。

## 3. 分层架构

三个正交的轴。不要混在一起讨论。

```
┌─ 存储轴 ────────────────────────────────────────┐
│L0 进程内    agent.messages           已有│
│ L1 跨会话   ~/.neo/sessions/*.json                已有，未利用│
│ L2 项目级   <cwd>/.neo/memory/                待建   │
│ L3 用户级   ~/.neo/memory/                       待建   │
└──────────────────────────────────────────────────┘
┌─ 粒度轴 ────────────────────────────────────────┐
│ 全文（project.md / user.md）                     待建   │
│ 条目（memory/*.md，一条一事实）                    待建   │
└──────────────────────────────────────────────────┘
┌─ 生命周期轴 ────────────────────────────────────┐
│ 人工写                待建                          │
│ 自动抽取              待建                          │
└──────────────────────────────────────────────────┘
```

**核心设计决策一：分层存储，不做单一记忆库。**

理由：项目约定的生命周期跟用户偏好完全不同。项目约定跟着 git 走，应该能提交、能review、能bisect；用户偏好跟着人走，跟哪个项目无关，混进项目文件是污染。把它们放同一个库，总有一个要妥协。

**核心设计决策二：条目粒度，而非全文。**

这是决定Q3 能不能答对的关键。一条记忆 = 一个可独立成立的句子 + 一组检索标签。

```
❌ 全文式：把整个 AGENTS.md 塞进去
   → 无法排序，无法按需加载，无法部分更新，长了就全废

✅ 条目式：
   {正文: 「部署前必须先跑 bun run check，CI 会卡」,
    标签: [deploy, ci, bun],
    来源: session:20261014-230259-i3tgr1,
    置信: 0.9}
   → 能按标签检索、能定位来源、能单独失效
```

对比`session.ts` 现有的JSON 结构，条目化几乎零成本 —— 会话本来就是消息数组，抽取只是从中切出子集。

## 4. 写入策略

### 4.1 三种写入，只有一种是自动的

| 方式 | 触发 | 风险 | 阶段 |
|---|---|---|---|
| 人工 `/remember` | 用户显式 | 无 | P0 |
| 抽取出候选，人确认 | 自动检测到信号 → 提示 | 低（有人看） | P1 |
| 抽取出候选，直接落盘 | 自动 | **高**（垃圾条目不可控） | P2，可默认关闭 |

**核心设计决策三：自动抽取默认需要确认，但确认成本必须极低。**

业界两种做法都有坑：
- Claude Code：后台抽取 + 直接写 `~/.claude/projects/<proj>/memory/`，终端只提示一声
- Mem0：ADD-only 语义（只追加不覆盖），带时间元数据

两者可以叠加 —— 采纳 ADD-only 语义（覆盖时新增一条并标记被替代者，不原地改写），但保留人工确认环节作为默认。

理由：记忆条目一旦落盘就会被后续每一轮注入。**一个错误条目的代价是它会持续误导未来的会话，且用户不会意识到。** 这与 config 里那个「静默套用模板密钥」的教训是同一类风险 —— 静默的错误比显式的错误贵得多。

### 4.2 什么信号值得抽取

不靠 LLM 猜。先用规则筛出候选，再决定是否调用 LLM 精炼。这样零成本，且可解释 —— 沿用 `RuleClassifier` 已验证的做法。

| 信号 | 判据 | 示例 |
|---|---|---|
| 显式偏好 | 用户说「不要/ 以后 / 记住 / 一律」 | 「回答不用加收尾语」 |
| 纠正 | 用户说「不对 / 不是这样 / 我说过」 | 对上一轮结论的否定 |
| 重复失败 | 同一工具同一错误 ≥2 次 | `edit_file` 的 old_string 不唯一 |
| 环境事实 | shell 输出里的稳定事实 | 项目用 bun 不是 npm |

**「重复失败」这条最值得先做** —— 它零成本、完全可解释、且失败模式最清晰。而且它复用了 `agent.ts` 里已经存在的 `consecutiveFailures` 计数器。

### 4.3 抽取的LLM 调用放在哪

`classifier` 的经验可以直接复用：**固定绑外部指定provider**（`classifier_provider`，即 ipsa 零成本网关），绝不用记忆抽取结果决定自己跑在哪。

抽取是分类/摘要问题，不是推理问题，成本敏感但智力要求低。这与 `system-prompt.ts` 里已有的设计理由一致。

## 5. 读取策略（最关键的一节）

### 5.1 分档预算，不做全量

```
上下文预算 = context_window × compact_threshold
200000 × 0.75 = 150000 tokens

分配：
  L2+L3 记忆常驻上限   2000 tokens   （~1.3%，硬上限）
  L0 对话              其余
```

2000 tokens 大约是 40~60 条中等长度条目。**这个数字是拍的，需要实测校准** —— 见第 8 节。

超过上限时的处理，按优先级排序：

| 优先级 | 内容 | 行为 |
|---|---|---|
| P0 | 显式 `/remember` 写入的条目 | 永不丢|
| P1 | 带当前任务相关标签的条目 | 优先保留 |
| P2 | 其余条目 | 按「最近命中时间」裁剪 |

裁剪发生时**必须告知**。静默裁剪等于让用户以为记忆还在。

### 5.2 检索：先不引入向量

**核心设计决策四：v1 只做标签匹配 + 关键词，不上embedding。**

理由：
- 向量检索需要额外的 embedding 调用。ipsa 网关的 embedding 能力**未验证**（`/models` 返回 7 个模型，未确认是否有 embedding 类）。
- 记忆条目量级是几十到几百条。在这个量级下，标签匹配 + 关键词的召回率与向量检索差距很小，但成本和延迟差一个数量级。
- 关键词匹配可解释，能回答「为什么这条被选进来了」。

演化路径留好接口：`retrieve(query, tags) => Entry[]`，v2 要换实现时改函数体，不改调用方。这与 `TierClassifier` 的接口化是同一个思路 —— 已在项目里验证过收益。

### 5.3 注入位置

现有 `index.ts:332` 把记忆拼到 system prompt **尾部**。这里有 bug 风险：`noteModelChange()` 会用正则改system prompt 的「- 模型：」行。

建议：**注入成独立的第二条 system 消息**，而不是拼接进第一条。

```
messages[0] = system  基础提示词（可被 noteModelChange 安全改写）
messages[1] = system  记忆块（独立，noteModelChange 不碰）
messages[2...] = 对话
```

改动量小，且天然解决 1.2 里说的两类干扰。

## 7. 分期实施

**P0 — 只读，不写。** 这是最小可用且零风险的一步。

- `src/memory/store.ts`：读取 L2/L3 条目
- 注入为 messages[1]，带 2000 token 上限
- `/memory list` 查看当前生效的记忆 + 每条的来源
- **不自动抽取任何东西**

价值：立刻解决「没有 AGENTS.md 就完全裸奔」的问题。风险：只读，不写坏。

**P1 — 手动写。**
- `/remember <文本>` 手动写入条目
- `/memory forget <id>` 删除
- 标签自动从文本推断（关键词规则，不调 LLM）

**P2 — 自动抽取，人工确认。**
- 规则筛信号（第 4.2 节四条）
- LLM 精炼成条目格式，走固定 provider
- 终端提示候选，用户 y/n
- ADD-only 语义

**P3 — 检索优化。**
- 标签相关度排序
- 冲突检测（同一标签下的矛盾条目）

**明确不做（v1）：**
- 向量库 / embedding
- 知识图谱（Zep/Graphiti 那套）—— 单人CLI 工具的场景下运维成本远超收益
- 跨会话自动继承（`--resume` 已覆盖大部分需求）
- 记忆自修改（让模型改自己的记忆 —— 风险不可控）

## 9. 一页总结

1. **现状**：会话存了但从不提取；AGENTS.md 全量注入无上限，且当前环境根本没有这个文件。
2. **三个真问题**：给谁看（双层）、何时写（自动需确认）、何时读（分层预算，不是全量）。
3. **四个核心决策**：分层存储；条目粒度而非全文；自动抽取默认需确认 + ADD-only；v1 只做关键词不 上向量。
4. **接入**：新增 `src/memory/`，沿用 classifier 的接口 + 注册表结构；注入为 messages[1] 避开正则冲突。
5. **节奏**：P0 只读零风险 → P1 手动写 → P2 自动抽取（需确认）→ P3 检索优化。
6. **未验证**：token 预算、embedding 可用性、抽取质量——三项都需要实测，我没有拍脑袋当结论。
