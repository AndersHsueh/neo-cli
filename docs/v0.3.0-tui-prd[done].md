# v0.3.0 TUI PRD —— 底部常驻状态条 + Claude Code 式输入框

> 2026-10-25 · 状态：**已实现（待 simplify 审查收尾 + 提交）**
> 上游 v0.2.4（输入层）
> 定位：**不换渲染模型**（inline + 终端 scrollback，不引入 alt-screen），在底部加一块
> 「live 帧」：状态条常驻 + 自绘输入框。这是 v0.2.3「状态只在每轮结束打一次」的直接解法，
> 也是 v0.3 路线里 [[TUI进化路线-2026Q4]] 的「常驻状态」段。

## 0. 为什么现在做、为什么敢做

v0.2.3 / v0.2.4 把「输出不丢信息、输入能补全」补齐了，但两个体验硬伤还在：

1. **跑 3 分钟的 turn 全程无反馈**：唯一的时间 / ctx / token 指标是每轮结束后的 `showStats`，
   用户看不到「现在在干什么、跑了多久、上下文用了多少」。
2. **输入区不像 2026 年的产品**：提示符是一行 readline 文本，没有边界、没有模式提示、
   没有候选/状态承载位置。用户明确反馈「这是不好意思拿给团队用的根本原因」。

**敢做的依据**：M0 探针已在 bun 1.3.13 + 真 PTY 下验证了整套底层机制（见 §2），
不是凭调研猜。Alice 项目的翻车复盘与 qwen-code 的输入区实现（Ink + Static 历史区 +
底部 live 区）是设计参照（见 §1）。

## 1. 对标事实（qwen-code v0.15.6 / Claude Code classic）

- qwen-code 的输入框不是全屏，也不是「四边框」：**一条上横线（可带右侧标签）+
  输入行（prefix `> `，多行续行对齐）+ 一条下横线**，下面再一行 Footer
  （状态行 / 模式提示 / ctx 指示）。live 区由 Ink 每帧重绘，历史消息走 Static 一次性打印进
  scrollback。`BaseTextInput.tsx` + `text-buffer.ts`（视觉行/光标映射）+ `KeypressContext`。
- 关键取舍：**左右边框不要**。四边框会让「行宽恰好 = 终端宽」时自动折行错位，
  是社区反复踩的坑；qwen 只画上下两条横线，宽度数学退化为「规则行 = cols」。
- Claude Code classic 同样是「输入区固定底部 + 历史在 scrollback + 不 alt-screen」，
  但它自带更复杂的 renderer；neo 用「自绘 live 帧」复刻其交互，而不是引入 React/Ink。

## 3. 架构

### 3.1 三层，职责互斥

```
src/tui/buffer.ts   纯文本缓冲：insert/delete/移动/history/按显示列折行 + 光标映射（无 IO）
src/tui/keys.ts     按键归一化：raw keypress → 语义动作；bracketed paste 状态机（无 IO）
src/tui/frame.ts    live 帧渲染器：擦除/整帧重写/提交行进 scrollback/光标定位（只碰 stdout）
src/tui/composer.ts 输入区编排：buffer + keys + frame + 候选/历史/审批/select 模态
src/tui/status.ts   状态行：字段拼装、宽度降级、ctx 进度条（纯函数）
src/ui/dock.ts      Console ↔ frame 的桥：流式行缓冲、工具行 transient、spinner、notice
```

### 3.2 渲染模型（与 qwen/Claude Code 同构，不 alt-screen）

终端上永远只有两种内容：

1. **已提交区**（scrollback）：`❯ 用户输入`、`● 助手正文`、工具行、系统提示。
   只追加，不重画 —— `Cmd+F` / tmux copy mode 照常可用。
2. **live 帧**（屏幕底部）：可重画的固定区域，从上到下：
   - 可选：活动行（spinner + 当前工具/「思考中」）/ 候选提示 / notice；
   - `────────` 上横线（右端可带会话名/模式标签）；
   - 输入行（prefix `❯ `，多行续行两空格对齐，超过 N 行滚动窗口）；
   - `────────` 下横线；
   - 状态行：`model · tier · mode · ⎇ branch · ctx ▓▓░░ 42% · 00:42 · 12.4k tok`。

重画算法（P2 实证）：光标当前停在输入位置 → `CSI nA` 回到帧首 → `\r\x1b[0J` 清到屏尾 →
写出新增提交行/整帧 → `CSI nA` + `\r` + `CSI nG` 把光标放回输入位置。帧高可变，
每次重画都按「上一帧光标在帧内的行号」上移，提交行后把该行号归零。

### 3.3 与 Console 的接线（关键约束）

**所有写入必须经过同一个 frame 通道**，否则动画行/流式输出会把帧擦掉。做法：

- `ConsoleDeps` 增加可选 `dock`。有 dock 时：
  - `writeStream` → dock 的「行缓冲」：按完整行切分、按列折行后提交（ANSI 安全）；
  - `beginStream/endStream` → 同上（前缀 `● ` / `┌ think ` 作为 pending 行的一部分）；
  - `toolHeader/toolResult` → live 活动行（transient，可被下一个工具覆盖；失败则提交）；
  - `startSpinner/updateSpinner/stopSpinner` → 活动行（与工具行同一个 owner，复用 v0.2.3 的
    `yieldAnimationLines` 纪律）；
  - `line/blank` → 先提交 transient，再提交一行；
  - `flashNotice` → notice 行（底部闪现，不占用输入区）；
  - `confirm` → composer 的 ask 模态（不再用 `rl.question`）。
- 无 dock（非 TTY / `-p` / 管道）时，全部走 v0.2.4 原路径，**零退化**。

### 3.4 非 TTY 语义

`process.stdin.isTTY !== true` 时**完全不进 composer**：保留现有 readline 路径
（`printf '/help\n' | neo`、CI、`-p`）。live 帧、状态行、框线在非 TTY 下零输出。

## 7. 风险与降级

- **Shift/Ctrl/Alt+Enter**：只有终端主动发送修饰键信息（Kitty 键盘协议等）才可达；普通终端与 Enter
  同字节。主力换行键是 `Ctrl+J` 与行尾 `\`（已在 README/`/help` 写明）。
- **交互式 `!cmd`**：suspend/resume 已实现并保证 `!echo` 类命令前后输入框/状态行恢复；
  长子进程的 Ctrl+C 回显时序在 PTY 下不稳定，未自动断言（v0.3.1 改 pipe）。
- **resize**：best-effort 擦旧帧后重画；S15 覆盖 100→60 的帧行宽/串行，极端重排可能留旧行。
- **IME / 真实终端差异**：PTY 测不到 IME 候选窗（实现把硬件光标定位在插入点并隐藏、自绘反显块）；
  发布前需人工在 Terminal.app / iTerm2 输入中文验证候选窗位置。
- **帧与异步写竞争**：所有写入收敛到 dock/composer；simplify 审查专门查了「绕过帧的 write」。
  `flashNotice`/工具行/spinner/流式/审批全部走 dock 分支。
- **帧高于屏幕**：输入超过可视行数时只渲染窗口（保留光标行），不试图重排历史。
- **性能**：流式 chunk 高频到达；composer 的 render 由 8ms timer 合并，tick 250ms；
  simulate 审查见 §8（若发现每 chunk 全帧重画会按建议加缓存/节流）。
- **降级线**：若某些终端对 `\x1b[0J` 支持异常，退化为「逐行 `\x1b[2K` + 下移」；
  若 raw mode 不可用（非 TTY/异常终端），回退 v0.2.4 readline 路径。

## 8. simplify 审查记录（2026-10-25）

三阶段并发只读审查（复用 / 质量 / 效率各 1 个 reviewer，各自跑 `git diff` + 新文件），
聚合后按严重度处置。**复用 1 critical + 6 major + 4 minor；效率 1 critical + 3 major + 8 minor**；
质量审查见 §8.3（后补）。critical/major 全部处置或给出不采纳理由。

### 8.1 复用审查处置

| 来源 | 严重度 | 问题 | 处置 |

### 8.2 效率审查处置

| 来源 | 严重度 | 问题 | 处置 |
|---|---|---|---|
| eff | **critical** | 流式每提交一行：`erage+commit` 一次 write、8ms 后再整帧重画 → 帧空 8-10ms，20 行/s 时约 40-50% 时间底部是空的（tmux/SSH 无原子帧更明显） | `FrameRenderer.commitAboveAndRender(rows,state)`：擦帧+提交行+整帧+光标定位拼成**一次 write**；composer 的 commitAbove/commitActivity/commitUserInput 全部改走它。新增 `F1i` 单测断言「只写一次」 |
| eff | major | 每帧 `agent.contextUsage()`（estimateTokens 全量遍历 + toolSpecs stringify），128k ctx 时 1.3ms/帧 | index 里 500ms 节流缓存（状态行只需两位有效数字） |
| eff | major | dock pending 每 delta 全量 rewrap（O(L²)）；reasoning 通道无 240 阈值，8000 字符时 386ms/行 | dock 增加 240 字符软断（按空格，且不切断 ANSI 序列），pending 恒定 ≤240；正文原本有 StreamFormatter 阈值 |
| eff | major | 长输入时 `layoutBuffer` 每帧全量重算（2000 行 1.34ms/帧） | composer 增加 `layoutFor(text,cursor,width)` 缓存（文本/光标/宽度不变直接命中），composeInput / 上下键共用 |
| eff | minor | 失败详情/详情模式逐行 emit（最多 18 次 write） | `dock.commitLines()` + `failTool()` 批量一次 `commitAbove`；Console 详情模式收齐 rows 后一次提交 |
| eff | minor | 每帧防御性 displayWidth 测量 | 保留（4-16 行、开销可忽略；resize 后首帧需要），记录不采纳理由：过早优化会削弱兜底 |
| eff | minor | `stop()` 漏清 pasteTimer，退出后 ≤1s 仍可能插附件 | stop 里清 pasteTimer + pasteChunks |
| eff | minor | `await fileIndex.refresh()` 挡在首帧前（2 万文件 ~75ms，冷盘更久） | 改为 `fileIndexPreheat`：composer.start + 补写 banner 后再 await，首帧不再等索引 |
| eff | minor | pre-composer 行按回退宽度固化，resize 变窄只 truncate 会吃字符 | **部分不采纳**：dockHost.width 已优先 `process.stdout.columns`（PTY/真实终端启动时可用）；仅 columns 真 undefined 的极端场景按 80 折行，后续加 rewrap 需把 dock 改成存原始行，留 v0.3.1 |
| eff | minor | history 无上限；图片 chip 删除后附件驻留 | history 加 1000 条上限；附件在提交时由 `bindAttachments` 按 chip 是否存在过滤（index 既有逻辑），无需额外改 |
| eff | minor | PTY 两处固定等待占 7.8s | `slow` 场景 2.5s→1.3s（>1s 足够触发 0:01）；resize 场景改为 waitFor 「帧切到 60 列」而非 sleep |
| eff | minor | rows=小终端时回退 24 行会让帧比屏幕高 | `rowsCount` 接受任意 >0；`maxFrameRows = max(4, rows-1)`，input viewport / select viewport 同步夹紧 |
