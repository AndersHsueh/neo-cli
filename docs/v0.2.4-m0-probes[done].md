# v0.2.4 输入层 M0 探针

> 日期：2026-10-25
> 环境：**bun 1.3.13** · macOS arm64（Darwin 27.0.0）· 真 PTY：`mkfifo` + `cat fifo | script -q /dev/null /bin/sh wrapper`，PTY 内 `stty cols 100 rows 40`，子程序 `TERM=xterm-256color`
> 探针脚本：[scripts/readline-probe.ts](scripts/readline-probe.ts)（`bun run scripts/readline-probe.ts`，P1~P7 全 PASS；连跑两次结论一致）
> 方法：真 PTY 内跑一个最小 readline 子程序（同一文件 `--child` 模式），同时采集三类证据：①子程序侧 JSONL 日志（completer 调用与入参、`rl.line`/`cursor` 20ms 采样、keypress、line 事件）②终端**原始字节** ③最小屏幕缓冲（`\r` 回行首、`\x1b[2K` 清行、`\n` 换行）。每条结论都指向探针编号 + 原始输出行。
> PASS 约定：**PASS = 探针跑完并给出确定结论（结论可以是否定），FAIL = 证据不足/超时/互相矛盾**。这里要的不是「功能符合预期」，而是「bun 到底怎么表现」。

### 对 v0.2.4 的一句话

bun 1.3.13 的 `node:readline` 是**完整可用**的行编辑器（原生 completer、setPrompt、`rl.line` 含 `\n` 都成立），不是「残缺版」；真正要小心的只有三处：**非 TTY 流上根本不进行编辑器**、**没有 completer 时 Tab 会字面插入 `\t`**、**Ctrl+J 默认按 Enter 语义提交且默认监听顺序拦不住**。

## 逐项证据

以下「程序日志」是子程序写入的 JSONL 行（已截断长字段）；「原始」是 PTY 字节流经 `JSON.stringify` 后的形态；「屏幕」是屏幕缓冲的行。

### P1 原生 completer 是否生效（`p1`）

操作：`un` + Tab → Enter；清空后 `f` + Tab + Tab → Enter。子程序 completer：`"un"`→`[["unique.txt"],"un"]`，`"f"` 开头→`[["file1.txt","file2.txt"], line]`。

程序日志（原文）：
```
证据 [caps] {"terminal":true,"refreshLine":"function","setPrompt":"function","getPrompt":"function","historyIsArray":true,"promptText":"P1> ","stdinIsTTY":true,"stdinIsRaw":true,"columns":100,"rows":40,"term":"xterm-256color"}
证据 [单候选/日志] seq=8 t=282ms completer {"argc":1,"argTypes":[{"kind":"string","value":"un","json":"\"un\""}],"line":"un","lineJson":"\"un\"","rlLine":"un","rlCursor":2}
证据 [单候选/keypress] seq=9 t=282ms keypress {"phase":"after-readline","ch":"\t","chJson":"\"\\t\"","name":"tab","sequence":"\t","sequenceJson":"\"\\t\"","ctrl":false,"meta":false,"shift":false,"rlLineAfterReadlineHandlers":"unique.txt","rlCursorAfterReadlineHandlers":10}
证据 [单候选/state] seq=10 t=295ms state {"line":"unique.txt","lineJson":"\"unique.txt\"","cursor":10,"prompt":"P1> ","historyTop":[]}
证据 [单候选/屏幕] ["P1> unique.txt"]
证据 [单候选/原始] "unique.txt"
证据 [单候选/提交] seq=11 t=555ms line {"line":"unique.txt","lineJson":"\"unique.txt\"","rlLineAfterSubmit":"","cursor":0}
证据 [多候选/第1次后 state] seq=18 t=755ms state {"line":"file","lineJson":"\"file\"","cursor":4,...}
证据 [多候选/第2次日志] seq=19 t=971ms completer {"argc":1,...,"line":"file","lineJson":"\"file\""}
证据 [多候选/屏幕] ["P1> unique.txt","P1> file","file1.txt  file2.txt","P1> file"]
```

结论：
- completer 被调用，入参 1 个（`line`，且是**光标前**的切片）。
- 单候选：`"un"` → `"unique.txt"`，**不追加空格**；Enter 提交 `"unique.txt"`。
- 多候选：第 1 次 Tab 展开公共前缀 `"file"`（不是展开全部候选）；第 2 次 Tab 打印列表 `file1.txt  file2.txt`，line 不变、**bell=0**。
- 空候选时终端无任何输出（无铃声、无提示）。

### P2 completer 入参 + 异步（`p2`）

三个独立进程，同一套 `createInterface`，只改 completer 形态：

| variant | completer 声明 | 观测 |
|---|---|---|
| sync | `function (line)` 返回数组 | `argc=1`，`argTypes=[string]`；Tab 后 `line="alpha.txt"` |
| async-callback | `function (line, cb)` | `argc=2`，`argTypes=[string, function(length=2)]`；10ms 后 `cb(null,[["beta.txt"],line])`；Tab 后 `line="beta.txt"` |
| promise | `function (line)` 返回 `Promise` | `argc=1`、`returnKind="Promise"`；Tab 后 `line="g"` 不变、原始字节为空、**无 `Tab completion error`**（静默丢弃） |

原文：
```
证据 [async-callback/completer] seq=7 completer {"argc":2,"argTypes":[{"kind":"string","value":"b"...},{"kind":"function","length":2}],"callbackType":"function"}
证据 [async-callback/callback] seq=9 completer-callback-invoked {"variant":"async-callback","line":"b"}
证据 [async-callback/state] seq=10 state {"line":"beta.txt","lineJson":"\"beta.txt\"","cursor":8,...}
证据 [promise/completer] seq=7 completer {"argc":1,...,"variant":"promise","returnKind":"Promise"}
证据 [promise/state] seq=6 state {"line":"g","lineJson":"\"g\"","cursor":1,...}
证据 [promise/原始] tabCompletionError=false raw=""
```

结论：入参是 `line`（异步时第二参为 callback），**没有 cursor 位置参数**；异步只支持 **arity=2 的 callback 形式**；返回 Promise 不被 `await`，静默无效（v0.2.4 如果用异步补全必须用 callback 写法）。

### P3 Tab 与自家 keypress / HotkeyRouter（`p3`）

子程序用**生产代码** `HotkeyRouter`（[src/hotkeys.ts](src/hotkeys.ts)）attach，并在 router 之前再挂一个原始 keypress 日志作为 witness。

阶段 1（`un` + Tab）原文：
```
证据 [阶段1/顺序] completer@8 → keypress@9 → router-tab@10
证据 [阶段1/keypress] seq=9 keypress {"phase":"after-readline","ch":"\t","name":"tab","sequence":"\t","rlLineAfterReadlineHandlers":"unique.txt"}
证据 [阶段1/router-tab] seq=10 router-tab {"tabCount":1,"rlLine":"unique.txt","rlCursor":10}
证据 [阶段1/提交] seq=12 line {"line":"unique.txt"}
```

阶段 2（`fi` + Tab，router 的 tab 回调里把 `rl.line` 改成 `"MUTATED"`）：
```
证据 [阶段2/router-tab#2] seq=20 router-tab {"tabCount":2,"rlLine":"file","rlCursor":4}
证据 [阶段2/state] seq=22 state {"line":"MUTATED","lineJson":"\"MUTATED\""...}
证据 [阶段2/提交] seq=23 line {"line":"MUTATED","lineJson":"\"MUTATED\""}
```

补充子观测（决定「路线 B 怎么接」）：
```
证据 [none/router-tab] seq=9 router-tab {"variant":"none","rlLine":"un\t","rlCursor":3}
证据 [none/state] seq=10 state {"line":"un\t","lineJson":"\"un\\t\"","cursor":3,...}
证据 [noop/completer] seq=8 completer {"argc":1,...,"variant":"noop","line":"un"}
证据 [noop/router-tab] seq=10 router-tab {"variant":"noop","rlLine":"un","rlCursor":2}
证据 [noop/state] seq=7 state {"line":"un","lineJson":"\"un\"","cursor":2,...}
```

结论：
- Tab 同时触发原生补全与 keypress，**顺序由监听器注册顺序决定**：readline 构造时注册的内部监听器最先（completer 在它里面跑），其后才是 HotkeyRouter 的 keypress 监听。所以 router `"tab"` 回调看到的是**已经补全完**的 `rl.line`。
- 在 router 的 tab 回调里改写 `rl.line` + `_refreshLine()` 可以覆盖最终提交（实测提交 `"MUTATED"`），等于「先补全再擦掉重画」，会有一次多余重绘。
- **neo 现状（不传 completer）：Tab 会把字面 `\t` 插进行缓冲**，`rl.line` 变成 `"un\t"`——这是可复现的存量行为，不是猜测。
- 传一个返回空候选的 no-op completer 可以把原生 Tab 干净吞掉（`rl.line` 保持 `"un"`，completer 仍会被调用一次），这是路线 B 推荐的前置条件。

### P4 Ctrl+J（0x0A）与 Enter（0x0D）（`p4`）

默认注册顺序（`createInterface` 之后才 `emitKeypressEvents`+挂监听）：
```
证据 [默认顺序/Ctrl+J 日志] ["seq=9 line {\"line\":\"abc\",\"lineJson\":\"\\\"abc\\\"\"}",
                          "seq=10 keypress {\"ch\":\"\\n\",\"name\":\"enter\",\"sequence\":\"\\n\",\"ctrl\":false,\"rlLineAfterReadlineHandlers\":\"\"}"]
证据 [默认顺序/Ctrl+J 原始] "\r\r\n\u001b[1G\u001b[0JP4> \u001b[5G"
证据 [默认顺序/Enter 日志] ["seq=16 line {\"line\":\"def\"}", "seq=17 keypress {\"ch\":\"\\r\",\"name\":\"return\",\"sequence\":\"\\r\",\"ctrl\":false}"]
```

预注册顺序（**在 `createInterface` 之前**调用 `emitKeypressEvents(process.stdin)` 并挂监听，然后构造 rl；监听器顺序变成 我们 → readline 内部），在 pre 监听里把 Ctrl+J 的 `key.name` 改写成 `"escape"`（内部 `_ttyWrite` 对该 name 直接 return），再在 post 监听里把 `"\n"` 塞进 `rl.line`：
```
证据 [预注册/Ctrl+J 日志] ["seq=12 pre-keypress {\"ch\":\"\\n\",\"name\":\"enter\",\"sequence\":\"\\n\",\"rlLineBeforeReadlineHandler\":\"abc\"}",
  "seq=13 pre-keypress-intercept-ctrlj {\"nameBeforeMutation\":\"enter\"}",
  "seq=14 pre-keypress-mutated {\"nameAfterMutation\":\"escape\",\"sequence\":\"\\n\"}",
  "seq=15 post-keypress-ctrlj {\"name\":\"escape\",\"sequence\":\"\\n\",\"rlLineAfterReadlineHandlers\":\"abc\"}",
  "seq=16 ctrlj-newline-inserted {\"lineJson\":\"\\\"abc\\\\n\\\"\",\"cursor\":4}"]
证据 [预注册/Ctrl+J 原始] "\u001b[1G\u001b[0JP4pre> abc\r\n \u001b[1G"
证据 [预注册/最终提交] seq=26 line {"line":"abc\ndef","lineJson":"\"abc\\ndef\"","rlLineAfterSubmit":"","cursor":0}
证据 [预注册/最终 state] seq=28 state {... "historyTop":["abc\ndef"]}
```

结论：
- Ctrl+J 与 Enter 在 raw mode 下**字节与 key 元数据都可区分**（`"\n"/"enter"` vs `"\r"/"return"`）。
- Ctrl+J 默认**提交一行**（`line` 事件 seq 小于后注册 keypress 的 seq，说明内部监听器先跑）。
- 想在**提交前**拦 Ctrl+J，必须在 `createInterface` 之前抢到 stdin 的 keypress（或 data）监听；拦截方式依赖内部 `_ttyWrite` 对 `key.name === "escape"` 的短路，属于实现细节（bun 升级需回归，本探针可当回归测试）。
- 被拦截改造后 `rl.line` 含 `\n`，后续输入正常追加，Enter 提交 `"abc\ndef"`；历史里会出现一条含 `\n` 的条目（`historyTop:["abc\ndef"]`）——做 continuation 时要像现有 paste-end 一样清理 history。

### P5 `rl.line` 能否容纳换行（`p5`）

操作：`xyz`（cursor=3）→ Ctrl+G 触发 `rl.line="a\nb"; _refreshLine()` → Ctrl+O 触发 `rl.cursor=2; _refreshLine()` → Enter；再 `xy` → Ctrl+T 触发 `rl.line="a\nbcdef"; _refreshLine()` 单独判定 cursor。

```
证据 [赋值前 state] seq=8 state {"line":"xyz","cursor":3,...}
证据 [set-line] seq=11 set-line-nl-done {"after":{"line":"a\nb","lineJson":"\"a\\nb\"","cursor":3},"cursorChanged":false,"refreshResult":"ok","prevRows":1}
证据 [赋值后 state] seq=12 state {"line":"a\nb","lineJson":"\"a\\nb\"","cursor":3,...}
证据 [赋值后屏幕] ["P5> a","b"]
证据 [赋值后原始] "\u001b[1G\u001b[0JP5> a\r\nb\u001b[2G"
证据 [set-cursor] seq=15 set-cursor-done {"after":2,"assignError":null,"refreshResult":"ok"}
证据 [改 cursor 后 state] seq=16 state {"line":"a\nb","cursor":2,...}
证据 [提交] seq=17 line {"line":"a\nb","lineJson":"\"a\\nb\"","rlLineAfterSubmit":"","cursor":0}
证据 [提交后屏幕] ["P5> a","b","P5>"]
证据 [set-long-line] seq=24 set-long-line-done {"before":{"cursor":2},"after":{"line":"a\nbcdef","lineJson":"\"a\\nbcdef\"","cursor":2},"expectedLength":7,"cursorAutoUpdated":false,"refreshResult":"ok"}
证据 [长行赋值后屏幕] ["P5> a","b","P5> a","bcdef"]
```

结论：
- `rl.line` 可以装 `\n`；`_refreshLine()` 按显示列重新计算行数并画两行（`prevRows=1`），**不是**把 `\n` 当普通字符吞掉。
- Enter 提交的 line 事件内容**完整包含 `\n`**（`JSON.stringify` 为 `"a\nb"`），不存在「只提交最后一段」。
- 直接赋 `rl.line` **不会**同步 `rl.cursor`：cursor=2 时赋 7 字符长行，cursor 仍是 2。要光标到末尾必须 `rl.cursor = rl.line.length` 再 `_refreshLine()`。
- 本探针未发现 cursor 错乱/渲染残影；多行提交后 `clearLine` 会把光标移到末行并换行，需要调用方自行 `rl.prompt()` 恢复提示符（子程序在 line 事件里这么做了）。

### P6 中途 `setPrompt` + `_refreshLine`（`p6`）

操作：输入 `hello` → Ctrl+G 触发 `rl.setPrompt("… "); _refreshLine()` → 继续输入 ` world` → Enter。

```
证据 [切换前 state] seq=10 state {"line":"hello","cursor":5,"prompt":"❯ ",...}
证据 [set-prompt] seq=13 set-prompt-done {"after":{"prompt":"… ","line":"hello","lineJson":"\"hello\"","cursor":5},"setError":null,"refreshResult":"ok"}
证据 [切换后 state] seq=14 state {"line":"hello","prompt":"… ",...}
证据 [切换后屏幕] ["… hello"]
证据 [切换后原始] "\u001b[1G\u001b[0J… hello\u001b[8G"
证据 [提交] seq=22 line {"line":"hello world","lineJson":"\"hello world\""}
证据 [提交后屏幕] ["… hello world","…"]
```

结论：`setPrompt` 只改内部 prompt 字符串，`_refreshLine` 用新 prompt 整体重绘；行缓冲与 cursor 保留，光标按新 prompt 宽度重算（`\x1b[8G` = "… hello" 的列位置），继续输入与提交均正常。生产里 `… ` 续行提示符方案成立。

### P7 补全后 ↑ 历史召回（`p7`）

操作：输入 `hello` 提交（造历史）→ `fi` + Tab（补全成 `file1.txt`）→ ↑ → ↓ → Ctrl+U → ↑ → Enter。

```
证据 [历史] seq=11 line {"line":"hello"}
证据 [补全] seq=17 completer {"argc":1,...,"line":"fi","historyTop":["hello"]}
证据 [补全后 state] seq=19 state {"line":"file1.txt","lineJson":"\"file1.txt\"","cursor":9,"historyTop":["hello"]}
证据 [补全后↑ keypress] seq=20 keypress {"name":"up","sequence":"\u001b[A","rlLineAfterReadlineHandlers":"file1.txt"}
证据 [补全后↑ state] seq=19（state 是否变化=false）
证据 [补全后↓ state] seq=19（state 是否变化=false）
证据 [Ctrl+U 后 state] seq=23 state {"line":"","cursor":0}
证据 [清空后↑ state] seq=25 state {"line":"hello","cursor":5}
证据 [最终提交] seq=26 line {"line":"hello"}
```

结论：
- 补全后直接 ↑ **不会**出现补全文本被吞或重复，但**也召不回历史**：readline 把当前 buffer `"file1.txt"` 当作历史前缀搜索条件，`"hello"` 不匹配，line 原样不动（state 无变化）。↓ 同理。
- 这是 readline 的历史前缀搜索语义（node 同源），不是 bug；交互上需要「先清空行再 ↑」或自行接管历史。
- Ctrl+U 清空后 ↑ 正常召回 `"hello"`；补全本身不写入 history。

## 与 Lead 初测事实的差异（照实写）

Lead 已实现自接管 Tab/Ctrl+J/continuation，下面只记录**观察差异**，不代表其实现有问题：

| Lead 观察 | 本探针结论 | 差异原因 / 说明 |
|---|---|---|
| **P1：`completer` 注册后从不被调用；Tab 当普通字符插进缓冲，提交 `"ab\tZ"`** | 真 PTY 下 completer **被调用**、Tab 触发补全；只有**不带 completer** 时 Tab 才字面插入 `\t` | **Root cause 已复现**：readline 的 `terminal` 默认取 `output.isTTY`。非 TTY（管道）时走 `_normalWrite`，根本不运行行编辑器 → completer 永不调用、Tab 是普通字符。用管道 1 行复现了 Lead 的字节：见下方命令。本探针 caps 行证明自己走的是 PTY 路径：`terminal:true stdinIsTTY:true stdinIsRaw:true`。**结论：P1 差异是「非 TTY 假 PTY」造成的，不是 bun 版本差异。** |
| P3：Tab 在 HotkeyRouter 侧可见 `{name:"tab", seq:"\t"}` | 一致；补充：Tab 同时触发原生补全、顺序见 P3 | 无差异 |
| P4：keypress 能区分 Ctrl+J/Enter；**但两者都触发 line 事件，且 keypress 与 line 先后顺序在分块边界不可靠** | 区分性一致；「都触发 line」一致。**顺序在本探针稳定**：同一 tick 内 line 事件总是先于「createInterface 之后注册」的 keypress 监听（连跑两次一致）。顺序真正取决于**监听器注册顺序**：预注册监听器会在 line 之前看到 Ctrl+J（P4 预注册实验）；若字节分块在同一 chunk 里带多个字符，只是同一 tick 内多次 keypress，不改变「每个按键：内部 handler → 后注册监听」的相对顺序 | 建议表述为「顺序由注册时机决定」而非「分块边界不可靠」；两者在工程上的结论相同：**默认顺序下拦不住 Ctrl+J，要拦必须预注册** |
| P5：`rl.line="a\nb"` 两行都画出、Enter 提交含 `\n`；**但 cursor 被拉到末尾** | 前两条一致；cursor 未复现「被拉到末尾」：赋 `"a\nb"` 时 cursor 保持赋值前的值（3，恰好=长度，看起来像末尾）；用 7 字符长行单独验证，cursor 仍停在 2（`cursorAutoUpdated=false`）。若要末尾需显式 `rl.cursor = rl.line.length` | 可能差异：赋值前 cursor 状态不同，或调用方在赋值后额外 `prompt()/clearLine()`。**工程结论一致**：多行场景不要依赖 cursor 自动跟随，必须手动设 |
| P6：`setPrompt` 可用，生产已用 `… ` | 一致 | 无差异 |
| P7：未系统测 | 已补两项路径：补全后 ↑/↓（无变化）、Ctrl+U 后 ↑（正常召回）；补全不进 history | 见 P7 |

非 TTY 复现命令与原文（用来解释 P1 差异）：

```bash
printf 'ab\tZ\n' | bun -e '
const { createInterface } = require("node:readline");
let calls = 0;
const rl = createInterface({
  input: process.stdin, output: process.stdout, prompt: "> ",
  completer: function (line) { calls++; return [["bingo"], line]; },
});
rl.on("line", (line) => { console.log("LINE " + JSON.stringify(line)); console.log("completerCalls=" + calls); rl.close(); });
rl.prompt();
'
# 实测输出：
# > LINE "ab\tZ"
# completerCalls=0
```

> 结论：**判断 readline 行为前必须先确认 `terminal:true` / `stdin.isRaw:true`**；PTY 拉起成功不等于子进程吃到了 TTY（Bun 的 `stdin:"pipe"` 是 socketpair，`script` 会报 `tcgetattr: Operation not supported on socket`；或子程序被包了一层管道）。

## 推荐实现路线

### 路线 A：用 readline 原生 `completer`

- **代价**：低。`createInterface({..., completer})` 传 `(line)`（同步）或 `(line, cb)`（异步 callback）。
- **bun 1.3.13 可行性**：✅ 实测生效（P1/P2）。
- **限制/风险**：
  - 入参只有**光标前的 line 切片**，没有 cursor 索引（要自己解析 `@`/`/` 前缀，但够用）；
  - 候选列表样式、宽窄、无匹配反馈都不可定制（无铃声；空候选静默）；单候选**不补尾随空格**；
  - 异步只能用 arity=2 callback，Promise 返回静默失效（P2）；
  - 原生补全与自家 Tab 处理会**同时发生**（P3）：保留 completer 就别再接 `HotkeyRouter.on("tab")` 做补全，否则双补全 + 一次多余重绘。
- **适合**：只要「Tab 补全路径 + 列表」且能接受默认样式时。

### 路线 B：自己接管 Tab（v0.2.4 当前方向）

- **做法**：`createInterface` 传 **no-op completer**（`(line) => [[], line]`）吞掉原生 Tab；`HotkeyRouter.on("tab")` 里读 `rl.line`/`rl.cursor`，自行算候选、写 `rl.line` + `rl.cursor` + `_refreshLine()`。
- **代价**：中（候选渲染、光标数学、无匹配提示、异步候选加载都要自管）。
- **bun 1.3.13 可行性**：✅ 实测可行（P3）。
- **必须注意**：
  1. **不传 no-op completer 时 Tab 会字面插入 `\t`**（P3 `none/state lineJson "\"un\\t\""`），这是当前 neo 的存量行为；
  2. router 的 `"tab"` 回调在原生补全之后，若 completer 不是 no-op，会先补全再被改写，产生 flicker；
  3. 写 `rl.line` 后必须同步 `rl.cursor` 再 `_refreshLine()`（P5）；
  4. 补全后用户按 ↑ 会被前缀搜索挡住（P7），要么清空行、要么自行接管历史。

### 多行路线 A'：continuation 状态机（推荐）

- **做法**：在 `createInterface` **之前**预注册 stdin keypress 监听（`emitKeypressEvents(process.stdin)` + `.on("keypress")`），记录「本次 line 来自 Ctrl+J」标志；line 事件里若标志为真则**不提交**：暂存当前行、`setPrompt("… ")`、`prompt()`；最终 Enter 时把暂存行用 `\n` 拼接后提交；复位 `setPrompt("❯ ")`，并清理 readline history 中被 Ctrl+J 提交的条目（参考现有 paste-end 的 `history.splice`）。
- **代价**：中低；需要给 HotkeyRouter 增加「preAttach（rl 创建前）」能力，或在 index.ts 里先手工挂一个 keypress 监听。
- **bun 1.3.13 可行性**：✅ 预注册实验证明能在内部 handler 之前拿到 Ctrl+J（P4），且不影响 Enter。
- **风险**：`Ctrl+J` 那一行会先按 Enter 语义回显并进 history（视觉上是「上一行已提交 + 新续行提示符」，可接受）；提示符复位、history 清理要成对做。

### 多行路线 B'：直接往 `rl.line` 塞 `\n`

- **做法**：预注册并拦截 Ctrl+J（把 `key.name` 改写成 `"escape"`，让内部 `_ttyWrite` 短路），然后 `rl.line += "\n"; rl.cursor = rl.line.length; _refreshLine()`；Enter 直接提交含 `\n` 的 line。粘贴等程序侧场景也可以直接塞 `\n`（P5）。
- **代价**：代码量最小，UX 最接近「真正的多行编辑」。
- **bun 1.3.13 可行性**：✅ P4 预注册实测提交 `"abc\ndef"`；P5 实测渲染两行、提交含 `\n`。
- **风险**：拦截依赖 bun readline 内部实现（`_ttyWrite` 对 `key.name==="escape"` 提前 return），bun 升级可能失效；cursor 必须手动维护；历史条目含 `\n`；多行 `clearLine`/重绘的边界行为需更多场景回归（本探针 P5 可作基线）。**若采用，务必把本探针加进 CI。**

### 推荐落点

1. **v0.2.4 保持「路线 B 自接管 Tab + A' continuation 状态机」**：Tab 的 UI 要求（候选列表/样式/无匹配提示/异步候选）原生 completer 满足不了；A' 不依赖内部 hack，风险最低。唯一立刻要补的是 **no-op completer**，否则 Tab 会往输入里插 `\t`。
2. 多行若产品坚持「单一输入缓冲、直接回车提交整段」的体验，可切 **B'**，但需要接受「依赖内部实现 + cursor 手管 + 历史含 `\n`」，并以 `bun run scripts/readline-probe.ts p4 p5` 作为升级回归闸门。
3. 单行输入（无补全）场景不需要 completer：但**必须知道** Tab 会插 `\t`（P3 none），若不需要 Tab 语义可忽略，否则加 no-op completer。

## bun 1.3.13 怪癖 / 注意点（含原文）

1. **非 TTY 流不运行行编辑器**：`terminal` 默认 `!!output.isTTY`；非 TTY 下 `completer` 永不调用、Tab 当普通字符、line 由 `_normalWrite` 切分。无报错。复现见上文命令（`completerCalls=0`、`LINE "ab\tZ"`）。
2. **没有 completer 时 Tab 落空穿透**：`_ttyWrite` 的 `"tab"` case 条件不满足时 fall through 到 default，把 `sequence "\t"` 当字符插入 `rl.line`（P3 `none` 子观测 `lineJson:"\"un\\t\""`）。无报错。
3. **Promise 形式的 completer 静默无效**：不会被 `await`，`kTabCompleter` 解构 undefined 直接 return（P2 promise 变体，`tabCompletionError=false`、无输出）。无报错——比报错更危险。
4. **`rl.line` 赋值不更新 `cursor`**（P5 `cursorAutoUpdated=false`）；`rl.line`/`rl.cursor` 是普通可写属性（P6/P5 均直接赋值成功）。
5. **`_refreshLine` / `setPrompt` / `getPrompt` 都在**（caps 行 `refreshLine:"function" setPrompt:"function" getPrompt:"function"`）；`_refreshLine` 是下划线私有 API，但 v0.2.3 D5 已在生产使用。
6. **line 事件不会自动重画提示符**：`_line()` 先 `clearLine()`（把光标移到末尾并写 `\r\n`）再 emit，调用方要自己 `rl.prompt()`。
7. **Ctrl+J 默认提交且默认顺序拦不住**（P4）；拦截必须在 `createInterface` 前预注册监听。
8. **历史前缀搜索**：补全后当前 buffer 被当作历史过滤前缀，↑ 召不回不匹配的历史（P7）。
9. **旁证（非证据）**：`bun -e 'const rl=require("node:readline"); rl.Interface.toString()'` 可以看到 bun 1.3.13 的 `node:readline` 是 node 源码的 JS 转译（`Interface`/`_tabComplete`/`_ttyWrite` 等可直接读），与上面所有行为吻合；但本文件的结论只以真 PTY 实测为准，源码只用于解释与设计探针。
10. 常见 PTY 踩坑（沿用 v0.2.3 §7）：macOS `script(1)` 不接受 Bun 的 `stdin:"pipe"`（socketpair → `tcgetattr: Operation not supported on socket`），必须 `mkfifo` + `cat fifo | script`；`COLUMNS` 环境变量不改变 `process.stdout.columns`，必须在 PTY 内 `stty cols/rows`。
