# neo 开发协作与交付规范

> 本文约定需求从进入到交付的协作方式，适用于个人维护与小团队协作。角色是逻辑职责，可以兼任；兼任不等于可以伪称已由他人独立评审。
>
> 本文是协作总览，不替代现有维护细则。改代码前仍须先读 [`docs/maintenance.md`](maintenance.md)；测试写法、隔离和豁免只以 [`tests/README.md`](../tests/README.md) 为准。若本文与既有细则或任务授权冲突，先暂停并请主理人确认，不自行放宽质量、审查、推送或发布限制。

## 1. 适用范围与目标

适用于缺陷修复、功能需求、重构、文档和发布。目标是：

1. **需求可追踪**：外部缺陷和下达任务有 GitHub Issue，改动、验证和合入结果能回到 Issue。
2. **质量可复查**：交付说明区分“已执行并通过”“未执行”“环境无法执行”，不以自述代替测试证据。
3. **协作不过载**：标准任务走完整闭环，小改动可合并沟通和记录步骤，但不跳过必要验证与审查。

个人维护可一人承担多个角色；需要独立复跑或审查时，由主理人指定审查者。已有明确授权的自我改进路径继续按 `docs/maintenance.md` §7.2 执行，不因本文新增前置流程。

## 2. 角色与 RACI

R = 执行，A = 最终负责，C = 会签/咨询，I = 知会。每项只能有一个 A；没有专职人员时，由主理人明确指定兼任者。

| 活动 | 主理人 | 产品 | 架构 | 工程 | QA |
| --- | --- | --- | --- | --- | --- |
| 需求澄清、验收标准与优先级 | C | A/R | C | C | C |
| 技术方案、边界与兼容性判断 | I | C | A/R | C | C |
| 实现、回归测试与交付说明 | I | C | C | A/R | C |
| 质量关卡、验收与独立复跑 | I | C | C | C | A/R |
| 评审、合入与 Issue 闭环 | A | C | C | R | C |
| 发布决策、版本与推送 | A/R | C | C | C | C |

- **主理人**：拆解任务、指定负责人、处理冲突和升级；未经其确认，不扩大范围、不合入、不推送、不发布。
- **产品**：维护问题定义、用户价值、范围和可验证的验收标准，不替工程宣称验证结果。
- **架构**：只在跨模块、公共接口、兼容性、权限或关键取舍时需要正式会签；局部改动无需额外设计文档。
- **工程**：控制改动范围，遵循改前基线、先红后绿、simplify 和全量闸门，完整报告实际结果。
- **QA**：按风险验收并复核证据；默认路径的独立复跑可由主理人或其指定审查者承担。

## 3. GitHub Issue：需求入口与优先级

### 3.1 入口与最小字段

外部缺陷和下达任务必须先有关联 Issue；已有明确授权的自我改进可不建 Issue，但不得编造编号。一个 Issue 只承载一个可验收目标，混合目标先拆分。

Issue 至少写清：

- 背景/问题；缺陷附实际结果、期望结果和可复现步骤。
- 验收标准；必要时写明不做什么。
- 优先级、负责人、已知依赖或风险。
- 验证建议；TTY 行为明确需要真 PTY 场景。

产品负责澄清需求，工程/架构可补充技术约束。信息不全时标记待澄清，不带猜测直接进入实现。

### 3.2 优先级

| 优先级 | 判定口径 | 处理方式 |
| --- | --- | --- |
| P0 | 正在造成数据丢失、严重安全/权限问题或核心功能整体不可用 | 立即升级主理人，暂停冲突工作；修复仍需验证和审查 |
| P1 | 核心流程严重受损、明确回归或当前版本必须交付 | 当前迭代优先处理 |
| P2 | 一般缺陷、常规功能和体验改进 | 按价值和依赖排期，默认级别 |
| P3 | 低影响优化、可延后的小改进 | 进入候补，不挤占高优先级工作 |

优先级由产品提出，主理人对排期冲突作最终协调。不得仅以“修起来快”提升优先级。

## 4. 分支、提交、PR 与评审

### 4.1 分支与工作区

- 大改动或并行开发使用独立 worktree；主工作区已脏时不在其上开工。
- 使用 neo 托管 worktree 时，沿用 `neo/<name>` 分支约定。有关联 Issue 时建议 `<name>` 使用 `<issue>-<短横线摘要>`，例如 Issue #123 对应 `neo/123-fix-resume-lock`；无 Issue 的自我改进使用简短动机名。
- `<name>` 遵守托管 worktree 的合法字符约束。同名目录已存在时先确认归属，不覆盖他人改动。
- 每次开工先确认基线和改动范围，不顺手修改无关文件或版本号。

### 4.2 提交

- 一个提交表达一个完整意图，避免把无关格式化、重构和功能混在一起。
- 摘要简洁说明行为或原因；可使用 `fix:`、`feat:`、`docs:`、`test:`、`refactor:`、`chore:` 等前缀，但不为了形式拆分合理提交。
- 有 Issue 时提交说明包含真实 `#N`；无 Issue 时写清动机。
- 提交前检查暂存 diff，不提交密钥、本地配置、`docs/evidence/`、worktree 或其他临时产物。

### 4.3 PR 与评审

团队协作默认用 PR 交付；已有授权的直接合入/自审路径按维护细则执行。PR 或等效评审记录至少包含：

1. 关联 Issue、改动范围及验收标准对应关系。
2. 改前基线、先红后绿和 simplify 的必要记录。
3. 实际执行命令与结果；`bun test` 写明 pass/fail/skip，不能只写“测试通过”。
4. 未执行项、环境限制、已知风险和遗留事项。
5. 涉及 TTY、配置、权限、协议或文档时，列出相应验证与同步情况。

评审者检查范围、正确性、测试覆盖、越界文件和证据，不以作者自报替代判断。默认路径须审查通过并按要求独立复跑后才合入；评审意见有结论、有回复，未解决前不合入。

本文不构成远程推送授权。需要推送分支或创建远程 PR 时，遵守维护细则和主理人给本次任务的明确授权。合入默认遵循 `--ff-only` 及 worktree 清理规则，合入后核对文件确实落在 `main`。

## 5. 交付流程

### 5.1 标准路径

适用于新功能、跨模块改动、公共行为/接口变化、权限与兼容性相关改动，以及范围不清晰的修复。

1. **建单与分诊**：创建/关联 Issue，明确优先级、范围、负责人和验收标准。
2. **Ready 检查**：满足 §6 的 DoR；需要时由架构会签方案和测试策略。
3. **隔离与基线**：按风险建立 worktree，在干净树运行 `bun run check`、`bun test` 并记录结果。基线不绿先停下确认。
4. **先红后绿**：先补能失败的测试/断言；TTY 行为先补 PTY 场景，再实现。
5. **简化与自验**：单独做 simplify，不夹带新行为；运行相关测试和类型检查。
6. **全量闸门**：代码交付前运行 `bun run verify`，以 `ALL GREEN` 为准，并检查 skip。
7. **评审与合入**：提交 PR/等效评审材料，处理意见，完成必要独立复跑后合入并清理 worktree。
8. **闭环与发布**：合入后更新 Issue；需要发布时走 §8，功能合入与发版提交分开。

### 5.2 BugFix / 小型需求快捷路径

仅适用于根因和边界清楚、影响局部、无公共接口/权限/兼容性变化的改动。可以：

- 将方案、DoR 和验证计划直接写在 Issue，不另开设计文档。
- 将架构会签降为按需咨询，将进度更新合并到 PR。
- 开发中先跑相关测试，再统一跑全量闸门。

不可以省略回归测试、必要审查、`bun run verify` 或 Issue 闭环。开始后发现跨模块或行为边界扩大，立即转标准路径。P0 可压缩沟通和排期，但不得把快捷路径理解为免验证、免评审。

纯文档且无行为变更时，检查事实、链接、diff 和授权范围即可，不强制运行代码闸门，不改版本、不打 tag；若文档修改伴随代码行为变化，按代码任务执行。

## 6. Definition of Ready / Definition of Done

### 6.1 Definition of Ready（可开工）

- [ ] 有真实 Issue，或明确属于可豁免 Issue 的自我改进。
- [ ] 问题、目标和验收标准清楚；缺陷有复现或可靠定位线索。
- [ ] 优先级、负责人、范围与主要非目标明确。
- [ ] 依赖、兼容性和风险已识别；需要的架构会签已完成。
- [ ] 知道应补哪些单测/PTY 场景，以及本任务需要哪些质量关卡。
- [ ] 工作区和基线可用，不与他人的未提交改动冲突。

### 6.2 Definition of Done（可交付）

- [ ] 验收标准有对应实现和验证证据，没有未声明的范围扩张。
- [ ] 新行为/修复有回归测试；遵循先红后绿和 simplify。
- [ ] 按 §7 完成关卡，结果和 skip 已如实记录；无未说明的失败。
- [ ] 用户可见行为、PRD、README、release note 等按需同步。
- [ ] 评审意见已解决，必要独立复跑通过，改动已按要求合入并核对。
- [ ] Issue 已更新/关闭，worktree 已清理；不发布则明确“不发版”。
- [ ] 未执行项、已知限制和后续事项已显式记录。

## 7. 质量关卡

| 场景 | 必做验证 | 通过口径 |
| --- | --- | --- |
| 代码开工前 | `bun run check`、`bun test` | 记录基线；已有失败不得混入本改动 |
| 代码提交/交付前 | `bun run check`、`bun test` | 类型检查零错误；测试记录 pass/fail/skip |
| 终端渲染、输入、覆盖语义等 TTY 行为 | 上述检查 + `bun run e2e` | 真 PTY 场景通过；手工操作不能替代 |
| 代码全量交付、默认路径独立复跑、发布前 | `bun run verify` | 三阶段完成并输出 `ALL GREEN` |
| 要求零跳过的验收 | `NEO_STRICT_SKIPS=1 bash scripts/verify.sh` | 有 skip 即失败 |

`bun run verify` 等价于执行 `bash scripts/verify.sh`，依次运行类型检查、单测和真 PTY E2E。任一阶段失败即停止；证据写入 `docs/evidence/<version>-{tsc,tests,pty}.txt`，该目录不入库。

- skip 默认只告警，不等于零覆盖；交付记录必须保留 skip 数和已知豁免。
- 相关测试或单测全绿不能称为“全量验证”。
- 环境不支持 bash/PTY 或验证未跑时必须明说并升级，不得声称通过，也不得自行降低验收标准。
- 测试的具体编写、隔离、平台豁免和真实 LLM 链路要求以 `tests/README.md` 为准。

## 8. 发布与交付清单

发布是独立决策，不因 PR 合入自动发生。发布前由主理人确认范围、权限和时机，并按维护细则完成：

- [ ] 功能已先合入 `main`，发布使用独立提交。
- [ ] 行为变化有对应版本/专题 PRD；无行为变化在 release note 说明。
- [ ] `docs/release-notes/vX.Y.Z.md` 包含发布日、基线 commit、关联 Issue、验证数字、证据路径和已知未做。
- [ ] `README.md` 的本版特性与实测基线已对齐；`.gitignore` 禁止项仍有效。
- [ ] 只修改 `package.json` 的 `version`，版本为 `X.Y.Z`。
- [ ] 发布前再次运行 `bun run verify`，确认 `ALL GREEN` 且证据前缀为 `vX.Y.Z`。
- [ ] 四件套一致：`package.json` 版本、annotated tag `vX.Y.Z`、release note、README 相关说明。
- [ ] 先提交含版本号的发版提交，再在该提交打 annotated tag；仅在获授权后推送指定 GitHub 远程和 tag。
- [ ] 发布后回到 Issue 记录版本/tag、合入 commit 和验证结果，完成关闭与通知。

## 9. 反馈回路与升级机制

- **需求反馈**：范围或验收变化写回原 Issue，由产品更新，主理人评估排期；不在 PR 中静默扩 scope。
- **评审反馈**：在 PR/评审记录中逐条回应；修复后重跑受影响关卡，行为变化不得只改测试让红灯消失。
- **质量反馈**：闸门失败保留原始输出，区分基线失败、本改动回归和环境问题；新问题另建 Issue 并关联来源。
- **交付反馈**：合入和发布结果回写 Issue；release note 记录已知未做，不把遗留问题写成完成。

出现以下任一情况立即暂停并升级主理人：需求/验收无法达成一致；涉及权限、安全、数据丢失或公共兼容性；基线异常或验证反复失败；环境无法完成必要关卡；任务范围明显扩大；需要越权推送、合入或发布。产品裁决需求含义，架构裁决技术边界，QA 判定质量证据是否充分，主理人协调优先级和最终交付。

## 10. 文档与工作区记录

- 维护流程唯一入口为 `docs/maintenance.md`；测试约定唯一来源为 `tests/README.md`，本文不复制其详细测试规则。
- 行为 PRD 使用 `docs/<主题>-prd.md`，完成后按既有体例改为 `docs/<主题>-prd[done].md`；发布说明放 `docs/release-notes/vX.Y.Z.md`。
- 过程状态以 Issue/PR 为主，长期有效的决策落项目文档；临时讨论、个人凭据和本地运行输出不入库。
- `docs/evidence/` 是本地验证证据，不 `git add`；判断验证是否发生要看实际输出，不看规范是否写过。
- worktree 只用于文件隔离，不是安全沙箱；合入后仅清理确认归属的托管 worktree，有未提交改动时不得强删。
- 不提交 `settings.json`、备份配置、`.env*`、密钥、`bot-comments/`、`.neo/worktrees/` 等维护细则禁止项。
- 本文新增的是协作约定，不回溯描述为项目既往事实；后续调整规则时同步注明变更，避免多份文档出现冲突口径。
