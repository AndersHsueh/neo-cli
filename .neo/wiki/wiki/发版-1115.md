### #62：为什么它是最小改动面的一条

三个现成地基决定了它便宜：`src/tui/composer.ts` 的 `suspend()`/`resume()`（`!cmd` 跑外部进程用的同一套让 tty 机制）、`src/tui/keys.ts` 的 `mapKey()` 键位归一化、`src/tui/buffer.ts` 的 `setText()` 回填。新增 `src/editor.ts`（纯解析 + 临时文件 + spawn），`Ctrl+G` → `ctrl-g` → 挂起 → 跑编辑器 → 恢复 → 回填。

三处**刻意**的决定：

1. **命令不经 shell 解释**：argv 直传 spawn，所以 `EDITOR="code --wait"` 可用，而 `EDITOR="x && rm -rf /"` 不会被解释 —— 不引入命令注入面。
2. **失败一律保住原草稿**：编辑器非 0 退出 / 起不来 / 内容为空，都只给一句可读提示，输入框内容**原样不动**。空内容覆盖用户已写的东西是不可逆的数据损失。
3. **临时文件用完即删**：提示词可能含敏感内容，`finally` 里连目录一起删。

### #56：Notification 事件是「沿骨架长肉」

hooks 基础设施（`src/hooks/types.ts` 的 `HOOK_EVENTS`、`src/hooks/runner.ts` 的超时/进程组 kill/失败隔离、`/hooks` 遍历渲染）已落地，新增第四个事件不需要新体系。

三处**语义**决定（都是我拍板的，Cypher 已落地）：

1. **matcher 匹配的是「触发原因」不是工具名** —— `matchReason` 与 `matchTool` 分开命名、底层共用私有 `matchPattern`（只有语法相同，语义不同）。合成一个函数会让两种语义混在一个名字下。
2. **Notification 恒不阻断** —— 它是给人看的通知，没有模型要喂回原因；退出码 2 与 `onFailure=block` 在这里都不生效，失败只进诊断。
3. **`permission_prompt` 必须在 `ui.confirm` 之前发** —— 否则用户已经在点确认了通知才来，就失去意义。`turn_end` 通知先于 TurnEnd 发，同理：TurnEnd hook 自己失败不该拖住通知。

### 一次「测试脚手架静默吞掉整条链路」的教训

Cypher 交回 #56 时 9 条红，它自判是 provider/tier 问题。实际根因是**测试的 `makeCfg()` 缺 `maxToolIterations`**：`src/agent/loop.ts:600` 取到 `undefined` → `:630` 的 `for (let iter = 0; iter < maxIter; iter++)` 一次都不进 → 模型请求没发生 → 工具没派发 → `approve()` 没被调 → 审批框没弹。表征是「fake chatStream 从没被调用」「errorMessage=本轮在重试/迭代上限处结束」。

值得记的是这类故障的**静默性**：缺一个配置字段不是报错，而是让整条链路安静地不跑。`tests/hooks.test.ts` 那份完整 `makeCfg()` 存在的原因就在这儿 —— 教训是「抄整段，别手抄一份」。同理，Cypher 报的 `SpyIO` 漏 `blank()`、漏 `import { afterAll }` 也都是这类夹具缺口。

### #61 的三条硬约束

1. **不入历史**：请求走 `this.messages` 的**快照**（`[...this.messages]`，过滤召回注入的临时消息），绝不 push 回主 messages —— 它是活引用（工具循环/失败重试/降级重发都复用同一份），push 会污染主上下文并随 session 落盘。
2. **不调工具**：`tools` 传空数组，模型只能纯文本回答。
3. **不打断主轮次**：独立的一次请求，不碰主循环的在途状态；用量走 `recordUsage` 显式记账，否则 `/cost` 少算。

oneshot（`-p`）模式明确不可用 —— 没有可持续的会话上下文。

### 并发写同一 worktree 会撞车

子代理 bg-3 与主代理**同时**在 `.neo/worktrees/issue-61` 写代码，产生了两份 `askSide`、两份 `case "btw"`、两条 `COMMANDS` 登记。`implementedCommandNames()` 按正则从源码收顶层 `case` 名，**重复名字会让 `registerCommand` 抛「斜杠命令 /btw 已注册」**，整个测试文件直接加载失败。

处置：另开隔离 worktree `issue-61b` 重做，源文件恢复后按「计数唯一」逐项核对（`grep -c 'case "btw"'` 必须为 1）再提交。

**教训**：并行写同一 worktree 之前必须先划清边界 —— 派工时要么给不同 worktree，要么明确「同一目录只有一方写」。子代理的调研产物（测试契约）可以复用，实现则要隔离。

### 两条测试自身的坑（不是实现缺陷）

- **E2「回答不入历史」**：假模型对主轮次与旁支返回**同一句话**，断言被主轮次自己的正文命中。修法：假模型内部按调用序号返回**不同**内容（`turn++` 放在假模型里，不放在 `send()` 前后）。
- **E4「主轮次在途时插问」**：没等主轮次真的发出请求就插问，插问抢到了「第 1 次调用」那个永不 resolve 的 promise —— 测的就不是「主轮次在途」而是「插问在途」。修法：等 `call !== 0` 再插问。

**教训**：断言「某内容不存在」时，要先确认**别处**也不会产出同一内容；断言并发语义时，要确认自己等的确实是目标那个 promise。

### 本轮的一条 git 教训（已入 AGENTS.md 踩坑节）

一次 `git commit --amend` 能把上一个提交的身份改没：发版时用 `sed` 替换 release note 里的占位符，替换值含 `/`（`Ran 2097 tests across 121 files`、`32 passed / 0 failed`）→ BSD `sed` 报 `bad flag` → `&&` 链在第一步就断了 → 后面的 `git commit --amend` 仍然执行，把**刚合入的 #56 提交**改写成了发版提交。后果：#56 的代码在 main 里、但提交信息与 hash 丢了；版本号、PRD 改名、README 数字全没进提交；tag 指向的提交里 `package.json` 还是旧版本 → §10 四件套不成立。

**修法**：在**独立 worktree** 重建发布链（`git worktree add -b rel/vX <good-commit>` → 在那里重做发版提交 → `git reset --mixed` 移 main → `git tag -f`），别在 main 上原地修补。本次 v0.4.86 最终就是用这个办法重建的，且用户拍板后顺带把 #61 并入同一版。
