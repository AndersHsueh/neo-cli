# 修复-1107-formatTokens 末档 P 漏整数档

> 最后更新:2026-11-07

## 摘要

2026-11-07（v0.4.45）。`formatTokens` 的 P 档末档只写了 `fixed1(v / 1e15)`，漏了「整数档」那一半：`fixed1` 只把 `10.0` 降级成 `10`，不负责把 `1000.0` 收成整数。实测 `1e18 → "1000P"`、`1e19 → "10000P"`、`1e21 → "1000000P"`，宽度随数量级无限增长，与 k/M/G/T 档的「<10 一位小数 / ≥10 整数」两档结构不一致。这是 v0.4.31（M 档）、v0.4.44（T 档）之后的**第三次同类缺陷**：每次补新档都只补了「一位小数档」，忘了末档/新档也需要整数档。

修法：P 档拆成 `<10P` 一位小数 / `≥10P` 整数两支。`bun test` 1153 pass / 0 fail，`tsc` exit 0。

**已知未修（留作候选）**：≥1e21 时 `Math.round` 返回原值、`String()` 走科学计数法（`1e300 → "1.0000000000000001e+285P"`，301 字符）；`toFixed(0)` 同样在 1e21 以上退化（JS 规范）。彻底解决需末档封顶或十进制展开，属于改口径。

## 推理与依据

### 为什么是「第三次同类缺陷」

档位纪律写在 `src/ui/format.ts` 头部注释里，但**只写了「一位小数档进位到 10 降级」和「整数档进位到档宽升档」两条**，没有写「末档没有下一档可升，所以必须自己接住整数档」。于是：

- v0.4.31：M 档漏整数档 → `9_999_999 → "10.0M"`
- v0.4.44：T 档漏整数档 → `999_999_999_999_999 → "1000T"`
- v0.4.45：P 档漏整数档 → `1e18 → "1000P"`

三次的根因完全一致，都是「补新档时只写了 `fixed1` 那一支」。`formatBytes` 的末档 P 也有同样问题（`1024P → "1024P"`），但那里注释明确写了「末档 P 无处可升，保留 1024P」，是有意口径，未动。

### 为什么没顺手修 1e300

`Math.round(1e300 / 1e15)` 返回的是原值 `1.0000000000000001e+285`，`String()` 直接走科学计数法。试过 `toFixed(0)`，但 JS 规范规定 `toFixed` 在数值 ≥1e21 时返回 `toString()` 结果，同样退化。手工十进制展开（`toExponential` 拆尾数+指数再补零）能 work，但 `1e300` 会输出 301 个字符——状态栏「不折行」硬约束依然被打破。这说明真正的解法不是「把整数档写对」，而是「末档要封顶」，属于产品口径决策（封在多少？显示成 `>1000P`？），不在本轮「小而明确的代码缺陷」范围内。

### 探针先于改动

改前跑探针确认了实际输出，不是靠读代码推断。红测先失败（`Received: "1.0000000000000001e+285P"`），改完转绿，再跑全量。
