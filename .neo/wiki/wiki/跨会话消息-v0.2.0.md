# 跨会话消息-v0.2.0

## 摘要

v0.2.0 交付 neo 的跨会话消息：多个前台交互式进程通过 `~/.neo/mailbox/` 文件信箱互发纯文本消息，支持任意会话派活/回信/多跳协作，人可随时进入任意终端叫停补话。没有固定 leader；每个会话维护可查询的状态机与委派台账，发起方每 120s watchdog 检查接活方是否死亡/停滞/跑完不回信；消息在工具间隙（P1）或空闲 tick（P2）注入并自动开 turn。规格为 `docs/cross-session-messaging-prd[done].md`（2026-10-20 两轮裁决后的 v1.2）。v0.2.1 hotfix 修复主代理工具可见性（`isSubagent` 过滤）与长 turn 心跳/watchdog 误报。

> 最后更新:2026-10-20

## 用法

- 交互式 `neo` 启动即启用信箱；`-p` / 非交互不参与。
- `/rename <name>` 或 `--name <n>` 给会话起名；撞名自动 `-2` 后缀，dead 会话名字可复用。
- 模型工具：`send_message(target, body, reply_to?)`、`list_peers(target?)`；人类命令：`/peers [name]`、`/inbox`、`/inbox release <id>`、`/rename`。
- 回信带任务号：`reply_to` = 原消息 id；宿主按 receipts 自动填 `exec`（开始/结束/ms），发起方台账精确消账，不需要模型自己报时。
- 人工接管：任意终端 ESC 叫停；自动 turn 被 ESC 中止时不回滚历史，人类自己输入的 turn 保留回滚；补话后继续并回信上游。
- 交互 `/resume` 切换 session-id 时信箱身份同步改键；目标已 dead 则接管（按裁决丢弃未读），仍有活进程则拒绝迁移。

## 关键裁决（2026-10-20）

- **对等组网**：任何会话可发起/承接/多跳；`leader` 只是名字，不是进程属性。
- **ESC 裁决 A**：自动 turn 只停不删；人类输入的 turn 保留回滚。
- **失联检测**：watchdog 120s；心跳 15s；120s 无心跳判 dead；working 300s 无进展判 stuck；`outstanding` 区分「在等别人」与「跑完不回信」。
- **身份**：只认当前 session-id；进程没了就没了，未读不补投；投递 at-most-once。
- **-p**：不启用信箱（不建目录、不注册工具、不跑 tick）。
- **自动 turn 上限**：默认 20，每会话独立计数。

## 已知边界

- supervisor / 后台会话 / attach / agent view / 跨机留 v0.3。
- 多跳环靠每会话自动 turn 上限 20 + 发送端限流 + 接收端去重，无全局环检测。
- `reply_to` 缺失时退回「同 target 最早未回」近似；建议回信始终带任务号。
- 真实双终端 + 真实 LLM 的编排验收仍需人工在 TTY 下跑（单测用注入时间与 fake 消息覆盖）。

## 推理与依据

- 2026-10-20（session 20261020-205621-mbd4fb）：2026-10-20 实测发现 v0.2.0 跨会话消息的一个边界 bug：发起方 watchdog 判接活方 dead 的依据只有「心跳超时」，但接活方正在处理第一个 turn 时，心跳时间戳停在 turn 开始时刻，于是 watchdog 在 turn 尚未跑完时就误报 dead（本轮实例：jacky 心跳停约 234s 被报 dead，实际 `ps -p 41694` 进程存活、state 里 `phase: "working"`，正在处理收到的问候消息）。

修法（v0.2.1 已落地）：心跳独立于空闲 tick，turn 进行中每 15s 照常刷新；流式输出按 30s 节流计入 last_progress_at；`observePeer()` 增加 pid 存活探测，心跳超时但 `process.kill(pid,0)` 存活时降级为 `stale`，watchdog 不再报 dead。回归测试见 `mailbox-state.test.ts` E10/F8。

排查手法可复用：收到 dead 通知后先 `ps -p <pid>` 确认进程，再读会话 state 的 phase 字段，最后看 `last_inbound` 是否已被对方收取，三者交叉判断是误报还是真死。

- 2026-10-20（session 20261020-205625-7otggv）：2026-10-20 用两个真实会话（tom `20261020-205621-mbd4fb` ↔ 本会话）做了 v0.2.0 跨会话消息的端到端验证，结论：链路收发正常，完整闭环。

验证要点：
1. 收：tom 的握手消息 `msg-1792501226537-cij18y` 投递到本会话 inbox 并被当轮 turn 消费；`state.json` 的 `last_inbound`、`turn.source=mailbox`、`turn.from` 均正确落盘，消费后对方 inbox 清空。
2. 发：v0.2.0 时 `send_message` 被错误过滤出主代理工具清单，本会话用一次性脚本走 `Mailbox.send()` 正常发送路径（`src/mailbox/store.ts:137`）完成验证；v0.2.1 已修工具可见性，模型可直接调用 send_message。
3. 回执：回信 `msg-1792501377108-skml5n` 的 `reply_to` 带上对方任务号；exec 时长 149.6s 由 receipts 中「收到原任务」的时间自动算出，符合 PRD「模型不需要时钟」的设计。
4. 委派台账：对方回信后由 `resolveDelegation`（`src/mailbox/store.ts:286`）正常消账，不产生 watchdog 误报。

语义约定：纯打招呼类消息若不想让 watchdog 等回信，发送方应显式传 `expect_reply: false`；默认 `expect_reply` 在握手场景下也是合理的。

## v0.2.1 修复（2026-10-20）

真实双会话验证暴露的两个问题已修复：

1. **主代理工具可见性**：`toolSpecsFor()` 曾把子代理排除表套在所有 Agent 上，`task`/`compact_ctx`/`remember`/`send_message`/`list_peers` 全部被主代理过滤。改为只有 `isSubagent=true` 才过滤；主代理拿全量工具，system prompt 的「可用工具」行与启动横幅同步为 16 个工具。
2. **长 turn 心跳 / watchdog 误报 dead**：心跳独立于空闲 tick；流式输出节流刷新进度；pid 存活探测兜底。fake-LLM E2E 实测 3s 长 turn 中 `heartbeat_at > turn.started_at`，且请求 tools 数组含 send_message/list_peers。

验证：**523 pass / 0 fail（26 文件）**，tsc 零错误；发布说明 `docs/release-notes/v0.2.1.md`。
