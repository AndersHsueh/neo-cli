# 修复-1108-引用漏剥中文右括号

> 最后更新:2026-11-08

## 摘要

2026-11-08（v0.4.48）。`@path` 引用解析的 `TRAILING_PUNCT`（`src/input/completion.ts`）只剥 ASCII `)]}` 与全角句读（`，。；：、！？`），**漏了中文右引号/右括号/书名号**。中文用户写「（见 @a.ts）」时 path 变成 `a.ts）`，`exists()` 失败，引用**静默不展开**（不报错、正文里没有内容块）。ASCII `)` 剥、全角 `）` 不剥，是同一规则的两半，属枚举遗漏而非设计取舍。补 `）］｝〕〉》」』】〗〙〛｠` 到字符集。`bun test` 1157 pass / 0 fail（3666 expect，+12），`tsc` exit 0。未 commit。

## 推理与依据

### 为什么这轮没在 formatBytes/formatTokens 上继续挖

v0.4.44~47 连续四轮修的都是「数量格式化末档」同一族缺陷，本轮探针先扫了一遍 `formatBytes` / `formatTokens` / `truncate` / `formatDuration` / `clock` / `sanitizeOutput` / `hostOf` / `oneLine` / `progressBar` / `padEndW` / `wrapAnsi` / `truncateAnsi` / `tokenizeAnsi` 十余个纯函数，**常规区间全部正确**；剩下的异常（`1e300` 科学计数法）正是禁区里的末档封顶口径。于是换到输入层，在 `parseReferences` 上探到了这条。

### 探针怎么把它和「既定口径」区分开

```
"看 @package.json)"   => path: "package.json"      ← ASCII 右括号：剥
"看 @package.json）"  => path: "package.json）"    ← 全角右括号：不剥
"看 @package.json。"  => path: "package.json"      ← 中文句号：剥
```

三条并排看，`）` 的漏剥就无处可辩：同类的右括号 ASCII 剥、全角不剥，同类的句读中文剥。这不是「有意保留」，是枚举时只想到了 ASCII 括号。

### 为什么不是策略分叉

反方向（把 ASCII 括号也从集合里去掉，改成「一律不剥」）才是改口径 —— 那会让 `(@a.ts)` 失效，与既有测试 `C3a 解析 > 剥掉尾随标点` 直接冲突。补齐缺的那一半是修 bug。

### 为什么只剥尾部是安全的

`stripTrailingPunct` 用 `+$` 锚定尾部：`@a（b）.ts` 中间的括号不动。以右括号结尾的文件名（`@foo）.md`）本来就不是合法路径，剥掉不损失。

### 验证

- 红测：改前 `parseReferences("见 @a.ts）")` 的 path 是 `"a.ts）"`，期望 `"a.ts"`
- `bun test`：1157 pass / 0 fail / 71 files，3666 expect（v0.4.47 为 3654，+12；断言都在同一 `test()` 内，测试条数 +1）
- `bunx tsc --noEmit`：exit 0
- 证据：`docs/evidence/v0.4.48-tests.txt`、`docs/evidence/v0.4.48-tsc.txt`
- 改动文件：`src/input/completion.ts`、`tests/references.test.ts`、`docs/release-notes/v0.4.48.md`

### 本轮探到但判定「不可达」的两个候选

- **`nextDots` 域外返回值**：负数输入返回 `-1`/`-2`，`NaN`/`Infinity` 返回 `NaN`；而 `dotsText` 对同样输入做了 `((x % 3) + 3) % 3` 归一化，两者不对称。但 `nextDots` 唯一调用方 `ui/console.ts:450` 的 `toolDots` 在 `console.ts:442` 每次工具调用重置为 0 后只自增，**域外输入不可达**。属契约瑕疵。
- **`formatOutputLines` 窄宽溢出**：`room = Math.max(8, width - marginW - 2)` 在 `width < 10` 时输出超过终端宽度（探针实测 `width=8` 时 rowW=9）。但 `Console.cols()`（`ui/console.ts:142`）有 `n > 20 ? n : 80` 兜底，实际传入 width 恒 ≥ 21，**不可达**。

教训：探针能证伪「有异常」，但「异常是否可触达」要顺着调用链再查一层 —— 否则会去修一个用户永远碰不到的理论瑕疵。
