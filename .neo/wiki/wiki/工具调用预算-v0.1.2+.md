# 工具调用预算 v0.1.2+ — 每轮告知模型迭代上限

> 最后更新:2026-10-18

## 摘要

模型此前不知道存在工具迭代上限(`max_tool_iterations`,默认 40),会一直调工具直到被硬截断,用户拿到半截答案。修复分两半:上限 40 → 80;每次 LLM 请求前注入一条临时 system 消息告知「第 N 次 / 上限 80(剩余 80-N)」,剩余 ≤ 5 时追加明确次数并要求收敛。请求后(含 catch 路径)按引用移除,不进对话历史。commit `1edc374`,随 v0.1.3 发布(annotated tag 已推 gitee)。

## 1. 行为

每次请求,模型在消息末尾看到:

```
本轮工具调用：第 3 次 / 上限 80（已用 2，剩余 78）。
```

剩余 ≤ 5 时追加:

```
预算即将耗尽，仅剩 4 次工具调用机会。请停止继续探索，立即基于已有信息给出最终答案；
信息不足就在答案中明确说明缺什么，不要再用工具。
```

归零点在 `send()` 开头 —— 每次用户新输入时计数自然重置,对应「模型吐出最终答案、准备下一轮」。

## 2. 三个关键决策

**注入位置:临时 system 消息,不是 tools 数组。** tools 是静态 schema,掺文本会污染 `tool_choice` 语义,部分服务端还会校验 schema;system 是 OpenAI 兼容协议里最稳的旁路。消息在 `chatStream` 返回后立刻摘掉(成功与 catch 两条路径都摘),历史零残留。

**计数语义:iter+1(第几次 LLM 请求),不是 toolCalls。** `parallel_tool_calls=false`(`src/llm.ts:80`)下两者相等,但 iter 与硬上限严格对齐,不会出现「显示 5/80 而循环已跑到 78」的错位。

**剩余 ≤ 5 必须带具体次数,不能只写「即将耗尽」。** 只写耗尽,模型无法判断还能做几件事,往往继续探索,最后仍被截断 —— 提示就白做了。这是用户明确要求的。

## 3. 实现落点

| 落点 | 内容 |
|---|---|
| `neo/src/agent.ts` | `budgetMessage()` / `dropBudgetMessage()`;循环内 push → `chatStream` → pop |
| `neo/src/agent.ts:451` | 截断警告改为「本轮被截断 —— 上面的回答可能不完整」 |
| `neo/src/config.ts:452` | 默认值 40 → 80 |
| `settings.example.json:38` | 同步 80(`settings.json` 被 gitignore,本地另改) |

`dropBudgetMessage` 用 `lastIndexOf` 按引用比对,避免误删历史里内容恰好相同的消息。

## 4. 验证

- 全量 264 pass / 1 skip / 0 fail,tsc 干净
- mock `chatStream` 探针跑满 79 次请求:计数 1→80 递增、第 75 次起出现收敛提示且带具体剩余次数、历史零残留

## 推理与依据

### 补记：一次真实的绕行（2026-10-18，写入本段几分钟后）

- **现象**：写入上面这段经验后，发现「已用 N-1」的语义写得不精确（它数的是已完成的 LLM 请求轮数，不是工具调用次数），需要修正——于是直接用了 `edit_file` 改页面，**绕过了 `wiki_write`**。改动没有登记，直到写下这条补记才补登。
- **根因**：「写回只走 wiki_write」目前是 prompt 纪律（AGENTS.md 区块），不是硬工具闸门——raw 有 `assertRawImmutable` 硬拦截，wiki 主题页没有（主题页本该可改，`edit_file` 天然可达）。
- **边界确认**：这是方案的已知取舍，不是新 bug——raw 不可改做了真强制，wiki 页的「唯一路径」靠模型自律。本次绕行证明：自律在「急着修一行小错」时确实会失守，与方案里「劝告不如断言」的判断一致。
- **待办**：若要把 wiki 页写回也变成硬闸门，需在 `write_file`/`edit_file` 对 `.neo/wiki/wiki/` 目录做限制（引导走 `wiki_write`）。代价是用户手动编辑 wiki 页也会被拦——是否值得，留给用户拍板，暂记 todo。

### 运行期反馈：模型会把本消息误判为「泄漏」（2026-10-18，v0.1.4 发布会话实测）

- **现象**：同一会话内模型两次收到本消息（「第 1 次 / 已用 0」「第 4 次 / 已用 3」），第一次反应是怀疑「临时 system 消息泄漏进了对话历史」，拉着用户排查了一轮——查会话持久化、查输入回路、查 neo.sh，全部干净后才意识到方向错了。
- **根因**：这条消息的**设计收件人就是模型本身**——`budgetMessage()` 在每次 LLM 请求前注入，模型在感知流里看到它，恰恰说明机制在正常工作。误判的根源是「看到熟悉的文案就往 bug 方向想」，没有先核对注入时序。
- **识别方法**：对时间线即可。「第 N 次」= 本次是本轮第 N 次 LLM 请求；「已用 N-1」= 本轮已完成的 LLM 请求轮数（注意：一轮可含多个工具调用，别拿它对工具调用总数——2026-10-18 实测，一轮 4 次工具调用后消息显示「已用 3」）。数字吻合 → 正常注入，继续干活。只有两种情况才是真 bug：数字对不上，或这条消息出现在**持久化的会话历史**里（`dropBudgetMessage` 在成功与 catch 两条路径都会摘除，正常应零残留——已实测验证）。
- **元教训**：看到一段熟悉的文案，先问「这条消息的预期收件人是谁」。为模型设计的消息出现在模型感知里不是泄漏；为用户设计的消息出现在模型感知里才是。先核对设计意图，再决定要不要拉响警报。
